# 文書を Matcha / Matcha-D に書き起こす手引き

文法そのものは `../../matcha-default-extensions/references/matcha_grammar.md` にある。この手引きは、**ふつうの文章の論証**を Matcha に移すときの考え方と書き方の型をまとめたものである。

## 1. 論証の部品を見つける

文書を読み、次の部品に分ける。法律の文書でなくてもよい。法律以外では「根拠」が条文の代わりに原理・理論・経験則・データになる。

| 部品 | 問い | Matcha |
|---|---|---|
| 主張 | 文書は何を結論として言いたいか。誰（何）について言っているか | `#主張^根拠 <= 対象: ( … ) >> 結論 as ラベル` |
| 根拠 | その結論を支える規範・原理・法則は何か | `^根拠`（`#主張^根拠`、`%定義^根拠`） |
| 要件 | 根拠がその結論を出すには何が満たされる必要があるか | `「要件」`（原文の文言）、`%要件`（言い換え・定義） |
| 事実 | 要件にあてはめられている具体的な事実は何か | `<= 事実` |
| 評価 | 事実から要件を導くのに、どんな評価（解釈・判断）を挟んでいるか | `<= 事実@評価` |
| 論点 | 要件の意味について争いがあり、文書が一つの解釈を選んでいるか | `? 論点 => 規範 ~> 理由` |
| 例外・反論 | 原則を覆す事情、文書が退けた（あるいは認めた）反論は何か | 別の主張 + `!> $原則のラベル` |
| 優先 | 例外ではないが、対立する二つの主張のどちらが勝つと文書は言っているか | `:: 優先 $勝つ方 > $負ける方` |

**評価を見逃さない**。「AだからBである」の「から」の部分に、文書が明示しない判断が挟まっていることが多い。それを `@評価` として表に出すのが、Matcha に書き起こすことのいちばんの価値である（後の審査の対象になる）。

## 2. 書き方の型

### 2.1 基本形

```
#解雇の無効^労働契約法16条 <= 本件解雇: (
    「客観的に合理的な理由を欠き」 <= 遅刻は半年で2回だけである@合理的な理由を欠く
    「社会通念上相当であると認められない」 <= 注意も指導もなく即日解雇した@相当性を欠く
) >> 本件解雇は無効である as 解雇無効
```

- 一つの主張ごとに `as ラベル` を付ける（例外や優先で参照するため。参照しなくても付けておく）。ラベルは空白を含まない短い語にする。
- 改行で並べた要件は AND（すべて必要）として読まれる。どれか一つでよい場合は `|` で並べる（`&` と `|` を一つの並びに混ぜない。混ぜるときは括弧でまとめる）。
- 対象（`<=` の右）は、誰の・何についての主張かを書く。

### 2.2 例外と反論

原則と例外は、二つの主張にして `!>` で結ぶ。例外の結論は、原則の結論の否定（`>> not …`）にするのが基本である。

```
#解雇の有効^就業規則の懲戒規定 <= 本件解雇: (
    %懲戒事由 <= 甲は無断欠勤を続けた
) >> 本件解雇は有効である as 懲戒解雇

#解雇権濫用^労働契約法16条 <= 本件解雇: (
    「社会通念上相当であると認められない」 <= 欠勤は会社のハラスメントが原因だった@相当性を欠く
) >> not 本件解雇は有効である as 濫用 !> $懲戒解雇
```

- 文書が反論を**退けている**場合も、反論を主張として書く。そのうえで、退けた理由に応じて次のどちらかにする。
  - 反論の要件が事実で満たされない: 反論の主張に `!` を付け（`!#…`）、要件にも `!` を付ける。結論には不成立からの帰結を書く（§2.4）。
  - 反論は成り立つが、原則のほうが優先する: `:: 優先 $原則 > $反論`。
- 二つの主張が対立していて、文書がどちらが勝つかを言っていない場合は、`!>` も `:: 優先` も書かない（複数の Extension になる。それ自体が分析の結果である）。

### 2.3 優先順位

```
:: 優先 $特則 > $一般則
```

文書が「特別法は一般法に優先する」「安全は効率に優先する」のように優先を述べている場合に使う。その根拠は `//` コメントに書く。

### 2.4 成否の印と、不成立の主張の結論

- 文書が「この要件は満たされる／満たされない」と判断している場合だけ、`+`（成立）と `!`（不成立）を要素の前に付ける。判断していなければ付けない。
- **Matcha の約束**: 不成立の主張（`!#…`）の `>>` には、成立した場合の効果ではなく、**不成立からの帰結**を書く。

```
!#緊急避難^刑法37条 <= 本件行為: (
    !「現在の危難」 <= 危険はすでに去っていた@現在の危難ではない
) >> 緊急避難による違法性阻却は認められない as 緊急避難
```

### 2.5 論点

文書が要件の解釈について立場を選んでいるときに使う。順序は `? 論点 ~> 理由 => 規範` で、規範の後に `<= 事実@評価` を続けてあてはめることもできる。

```
? 「やむを得ない事由」の意味 ~> 期間途中の解雇は期間満了時の雇止めより厳しく制限されるべきだから => %雇用を継続することが社会通念上著しく困難
```

### 2.6 法律以外の論証

根拠を原理・理論・データにすればよい。

```
#値上げの支持^需要の価格弾力性 <= 本件の値上げ: (
    %需要が価格に非弾力的 <= 過去の値上げで販売数は2%しか減らなかった@需要は非弾力的
) >> 値上げで売上は増える as 値上げ支持
```

### 2.7 主張の連鎖（前の結論を次の要件にする）

ある主張の結論を、別の主張の要件として使うときは、`$ラベル` を要件の位置に書く。mext は `$ラベル` を参照先の主張（それが成り立つこと）と必要十分に結ぶ。

```
#前提の主張^原理A <= 本件: (
    %要件 <= 事実@評価
) >> 中間の結論 as 中間

#最終の主張^原理B <= 本件: (
    $中間
    %別の要件 <= 別の事実
) >> 最終の結論 as 最終
```

結論の文言を要件として書き写す（`%中間の結論`）と、別の命題として扱われ、後の分析で `same` の判断が要る。連鎖は `$ラベル` で書く。

規範（定義）に `as` で名前を付け、別の事件で `$名前 <= 別の事実` と使い回すこともできる（原典の用例）。この場合は、同じ規範を新しい事実にあてはめる意味になり、元の事件のあてはめの結果は持ち込まれない。

```
#AはBに対抗できない^94条2項 <= 第一の取引: (
    「第三者」: ? 意義 ~> 外観を信頼した者の保護 => %当事者以外で外形を信頼して新たに利害関係を持った者 as 第三者の規範
)

#GはEに対抗できる^94条2項 <= 第二の取引: (
    「第三者」: $第三者の規範 <= Gは事情を知らずにFから土地を買った
) >> GはEに対抗できる as G対抗
```

### 2.8 いくつもの理由で同じ結論を支える

原文が同じ結論に複数の理由を挙げるとき、その理由どうしの関係で書き方を選ぶ。以下の例の `$理由A` 〜 `$理由C` は、それぞれの理由の主張に `as` で付けたラベルである（§2.7 の主張の連鎖）。デフォルト論理には「三倍強い」のような強さの度合いがないので、強さは次のどれかの質的な形で表す。原文がどの意味で理由を重ねているかを、対応表に書く。

**(a) 冗長性: どれか一つで足りる**（強さは「全部を崩さないと結論が消えない」壊れにくさとして表れる）

```
#禁止 <= 本件: (
    ($理由A | $理由B | $理由C)
) >> 結論 as 禁止
```

**(b) 累積: 一つでは足りないが、二つ以上で足りる**（「総合考慮」に近い）

```
#禁止 <= 本件: (
    (($理由A & $理由B) | ($理由A & $理由C) | ($理由B & $理由C))
) >> 結論 as 禁止
```

**(c) 相互補強: 一つずつでは反論に負けるが、合わさると勝つ**（強さは「どの反論に勝てるか」として表れる。デフォルト論理ではいちばん自然な表し方）

```
#禁止 <= 本件: (
    ($理由A | $理由B | $理由C)
) >> 結論 as 禁止
#総合 <= 本件: (
    $理由A
    $理由B
    $理由C
) >> 結論 as 総合
#例外 <= 本件: ( … ) >> not 結論 as 例外 !> $禁止
:: 優先 $総合 > $例外
```

同じ判断（たとえば「社会の便益から各人の義務へ進む」橋渡し）を複数の経路で使っているなら、評価の文言を同じにする。mext はそれを一つの判断として扱い、判断ごと外したときの感度も計算する。理由どうしが内容の上で同じ弱点を共有しているか（たとえば、どれも「社会の便益から各人の義務へ進む」同じ型の橋渡しか）は、書き起こしでは決めない。mext分析の段階で `[ai]` の `concern` / `distinct` として判断する。

### 2.9 引用と賛同を分ける

評論や論文では、他人の見解を紹介し、それに賛成したり反対したりする。「A 氏がそう述べた」ことと、「その主張が成り立つ」ことは別の命題なので、分けて書く。

```
// 出典: 第2段落「A 氏は、X だと述べている」
#A氏の見解 <= A氏: (
    %Xだと述べている <= A氏は著書でXだと述べた
) >> A氏はXだと主張している as A見解

// 出典: 第3段落「私もこれに賛成する。なぜなら Y だからである」
#著者の賛同^Y <= 本件: (
    $A見解
    %Yである <= 事実@Yである理由の評価
) >> X as 賛同
```

- 引用された見解の主張は、対象を「その論者」にし、結論を「…と主張している」にする。紹介しただけで著者が賛否を示していなければ、これだけにする。
- 著者が賛成するなら、別の主張として書き、`$ラベル` で見解を参照する。賛成の理由がなければ、その主張は要件一つになる（`lint` で「一段の主張」に数えられる。原文の論証が見解の権威だけに頼っているなら、それは原文の性質としてメモに書く）。
- 著者が反対するなら、見解の結論の否定を結論とする主張を書き、`!>` か `:: 優先` で関係を示す。

## 3. 忠実さと、補ったものの明示

- **`::` と `//`**: 原典の用例では、`::` は論証の一部としての見出し（`::（１）について`）、`//` は書き手の編集上の注記（`// 略`）である。書き起こしでも、`::` は原文の節立てを写すのに使い、`//` は出典や補った前提などの編集上の注記に使う。
- **道具に読ませる判断は `.matcha` に書かない**: mext はコメントの意味を読まない。結び方が原文に明示されているか、事実の種別（記述・仮定・確認済み・著者の主張）といった判断は、メモ（`X.matcha.md`）に表として書き、mext分析で `.mext` の `[ai]`（`connective`、`fact-kind`）に移す。AI の判断はすべて `[ai]` に集める、というのが mext の設計である。
- **結び方の根拠を作らない**: 日本語の文章では、理由や要件が「すべて必要」なのか「どれか一つでよい」のかが明示されないことが多い。手がかり（「すべて」「いずれか」「以上から」「総合すれば」など）がなければ、メモには「読み」と書けばよい。もっともらしい根拠を後から作ってはならない。どの読みが結論を左右するかは、`mext connectives` が示す。

- **原文の言葉を使う**。結論・要件・事実は、できるだけ原文の文言をそのまま（または最小限に縮めて）書く。言い換えたときは、その旨を対応表に書く。
- **出典のコメント**: 各主張の直前と、事実・評価の直前の `//` コメント（`//` は花房氏の連載の用例にある行コメント）に、原文のどこから取ったか（段落番号や、短い引用）を書く。

  ```
  // 出典: 第3段落「遅刻は半年で2回にすぎず」
  ```

- **`^根拠` は表示である**: `^根拠` に書いた条文・原理・理論の名前は、mext では主張の名前の一部として扱われ、独立に立証される前提にはならない（感度分析の候補にも入らない）。根拠そのものが争われる論証なら、その根拠を要件として書き（`%原理Aが成り立つ <= …`）、あてはめを示す。原文にない根拠を `^` に書くと、それが「表示だけの補った前提」になるので、書くなら「補った前提」として明示する。
- **補った前提**: 文書が明示していないが、論証が成り立つために必要な前提（隠れた前提）を足した場合は、その行の直前に `// 補った前提: 理由` と書く。補った前提は、後の審査で最も疑われるべきものである。むやみに補わず、論証の穴は穴のまま残してよい（穴であることを対応表に書く）。
- **落としたもの**: 修辞、背景説明、論証に関係しない部分は書き起こさない。何を落としたかは対応表に書く。

## 4. 変数がないことへの対処

Matcha には変数がない。「すべての労働者について…」のような一般的な規範は、文書が問題にしている具体的な対象ごとに主張として書く（対象が複数なら、同じ形の主張を対象ごとに並べる。ラベルも対象ごとに変える）。

## 5. よくある誤り

- 結論を要件の中に書いてしまう（循環）。
- 一つの主張に、別々の根拠による論証を混ぜる。根拠が違えば主張を分ける。
- 評価を事実として書く（「不当な解雇だった」は事実ではなく評価）。`<= 事実@評価` に分ける。
- `!>` の向きを逆にする。`X !> $d` は「X が d の例外」（X が勝つ）である。
- 文言の中に演算子の文字（`:` `<=` `>>` `@` `&` `|` `^` など。全角の `：` `＠` `＆` も同じ）を書く。原文の引用に含まれていても、構文エラーになるか、構造が変わる。「は」「、」などに言い換え、対応表にその旨を書く。
- 前の主張の結論を、次の主張の要件として文言で書き写す（§2.7 のとおり `$ラベル` で書く）。
- **事実の文を「 で始める**。`<=` の後の「 は要件の記法の始まりと読まれる（構文チェッカが警告する）。事実の文が発言などの引用で始まるなら、『』に替える（「「まじめにやれば」と述べた」ではなく「『まじめにやれば』と述べた」）。
- **英文の行末に「as 単語」を置く**（英語の文書の場合）。`as` は名前付けの記法でもあるので、事実の文が「… as drivers」で行末になると、"drivers" がラベルと読まれて事実の文が切れる（構文チェッカが警告する）。「… as drivers do」のように言い換える。ラベルは一語（`as plan` など）にする。
- **評価に要件をそのまま写す**（`%A <= 事実@A`）。事実から要件への判断が一段にまとめられ、mext からは中身が見えなくなる（`lint` が「同語反復の評価」として警告する）。原文がその間に置いている判断の段階を、中間の要件や評価の理由として書き分ける。原文が本当に一段で飛んでいるなら、それは原文の飛躍なので、メモにそう書く。
- **段落全体を一つの事実に要約する**。事実には、原文が事実として述べていることだけを書き、評価や推論を混ぜない（`lint` は事実の中の「べき」「すぎない」などの語を知らせる）。
- **弱い主張を強い主張にする**。原文が「示唆する」「…と感じる」「…かもしれない」と書いていれば、結論にもその強さを残す（「…が示唆される」）。強めて書くと、原文にない主張を作ることになる。
- 同じ命題を主張ごとに違う言葉で書く。同じ命題は同じ文言にする（違う文言にすると、後の分析で AI が同一視の判断をしなければならなくなる）。
