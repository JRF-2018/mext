# matcha-analysis（matcha分析）

文書の論証を Matcha / Matcha-D に書き起こす。決定論的なのは構文チェックだけで、書き起こしそのものはあなた（AI）の仕事である。

設計原理は「機械的に変換した部分を人が追えること」である。そのため、書き起こしの**どの行が原文のどこから来たか**、**何を補い、何を落としたか**を、必ず人が追える形で残す。

## 準備

- 道具は Python のパッケージ `mext` にある（依存ライブラリなし）。最初に `python3 -m mext.matcha_check --help` が動くかを確かめる。動かなければ、次のどちらかをする。
  - `pip install git+https://github.com/JRF-2018/mext` を実行する。
  - このスキルをプラグインとして入れた場合は、プラグインのルート（このスキルのディレクトリの 2 つ上）を `PYTHONPATH` に加える。
- 書く前に、次の二つを読む。
  - `references/writing_matcha.md`（このスキルのディレクトリ）: 文書を書き起こすときの考え方と型。
  - `../matcha-default-extensions/references/matcha_grammar.md`: Matcha / Matcha-D の文法。
- このスキルのファイルが手元にない場合（ほかの AI や、スキルを入れていない環境から頼まれた場合）は、https://github.com/JRF-2018/mext の `skills/matcha-analysis/` と `skills/matcha-default-extensions/references/` を読んで、同じ手順に従う。
- 引数: 文書のファイル（`.md` `.txt` など。以下 `X.md`）、または会話に貼られた文章。貼られた文章の場合は、まず `X.source.md` として保存し、利用者に名前の希望がなければ内容から短い名前 X を付ける。
- 出力は文書と同じディレクトリ（利用者が指定すればそこ）に置く: `X.matcha`、`X.matcha.md`。**原文のファイルは書き換えない**。

## 手順

### 1. 文書を読み、範囲を決める

- 文書の主な結論と、それを支える論証の筋を把握する。
- 文書に独立した論証が多い場合（目安: 主な結論が 4 つ以上、または 1 万字を超える文書）は、どこまで書き起こすかを決める。
  - 利用者に聞ける場合は聞く。選択肢の例: 「主な結論一つだけ」「主な結論すべて」「反論への応答も含めてすべて」。
  - 聞けない場合（非対話の実行など）は「主な結論すべて」にし、その旨を `X.matcha.md` の冒頭に書く。
- 文書が論証を含まない場合（純粋な記述、物語など）は、そのことを `X.matcha.md` に書いて終える。無理に書き起こさない。

### 2. 部品に分ける

`references/writing_matcha.md` §1 の表に従い、主張・根拠・要件・事実・評価・論点・例外・優先を拾い出す。

- 特に、「AだからB」の間に挟まっている**評価**を見つけて、`@評価` として表に出す。
- 文書が退けた反論も、主張として拾う（退け方に応じて `!` か `:: 優先` にする）。
- 文書が明示しない前提（隠れた前提）は、論証の筋に不可欠なものだけを補う。

### 3. `X.matcha` を書く

- `references/writing_matcha.md` §2 の型で書く。各主張に `as ラベル` を付ける。前の主張の結論を次の主張の要件にするときは、結論の文言を書き写さずに `$ラベル` で参照する（§2.7）。
- 文言に演算子の文字（`:` `@` `&` など）を入れない（§5）。
- ファイルの先頭に、次のコメントを書く。

  ```
  // 原文: X.md（題名や著者が分かれば書く）
  // matcha分析: AI（モデル名）による書き起こし。Matcha-D（!> / >> not / :: 優先、主張への as）は非公式の拡張。
  ```

- 各主張と各事実・評価の直前に `// 出典: 第N段落「短い引用」` を書く。
- 補った前提には `// 補った前提: 理由` を付ける。
- 成否の印（`+` / `!`）は、文書が成否を判断している場合だけ付ける。

### 4. 構文チェック（決定論的）

```bash
python3 -m mext.matcha_check --tree X.matcha
```

- エラーがなくなるまで直す。警告は、意図したものか確かめ、意図したものなら `X.matcha.md` に理由を書く。
- `--tree` の出力を見て、要件や結論が意図した要素につながっているかを確かめる（字下げの誤りは、エラーにならずに構造だけが変わることがある）。

### 5. 形の点検（決定論的、簡易）

書き起こしが文書の論証を写せているかを確かめるために、一度だけ Extension を計算する。

```bash
python3 -m mext init --solve X.matcha -o X.check.mext
```

- 文書の主な結論が、少なくとも一つの Extension（文書が支持する側なら preferred Extension）に含まれるかを見る。
- 含まれない場合は、原因が次のどちらかを判断する。
  - **書き起こしの誤り**（ラベルの付け忘れ、`!>` の向き、文言の不統一など）: `X.matcha` を直す。
  - **文書の論証そのものの穴**（要件を満たす事実が書かれていない、など）: `X.matcha` は直さずに、`X.matcha.md` に穴として書く。
- 同じ命題を違う文言で書いていないかも、`X.check.mext` の `[atoms]` で確かめる（直せるものは文言を揃える）。
- この点検は書き起こしのためのもので、論証の審査ではない。点検が済んだら `X.check.mext` は消してよい（残す場合は `X.matcha.md` でそう書く）。

### 6. メモ `X.matcha.md` を書く

日本語で、次の章立てで書く。

```
# matcha分析: X

## 1. 文書の論証の要約      … 主な結論と、それを支える筋（数行）。書き起こした範囲
## 2. 対応表               … 原文の箇所（段落・引用）→ X.matcha の行番号とラベル。言い換えた場合はその旨
## 3. 書き起こしの判断      … 何を評価（@）としたか、何を例外（!>）・優先（:: 優先）としたか、その理由
## 4. 補った前提           … 一覧と、補った理由。補った前提は後の審査で最も疑われるべきものであることを明記する
## 5. 落としたもの          … 書き起こさなかった部分と理由
## 6. 構文チェックと形の点検 … matcha_check の結果（出力を貼る）、主な結論が Extension に出るか、見つけた論証の穴
## 7. 次の一歩             … mext分析（mext-analysis）に進むときの注意（同一視が必要になりそうな文言など）
```

## 注意

- 会話への返答もファイルも、利用者の言語で書く（指定がなく判断できなければ日本語）。

- 書き起こしは解釈である。**原文にない主張を作らない**。原文の論証が弱いと思っても、強くして書き起こさない（弱さはそのまま写し、メモで指摘する）。
- 原文の文言を、論証の都合で書き換えない。縮める場合も意味を変えない。
- 法的な文書で条文・判例が引かれていれば `^根拠` に書く。引かれていなければ、あなたの知識で補わない（補うなら「補った前提」として明示する）。
