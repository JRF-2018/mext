# matcha-analysis（matcha分析）

文書の論証を Matcha / Matcha-D に書き起こす。決定論的なのは構文チェックだけで、書き起こしそのものはあなた（AI）の仕事である。

設計原理は「機械的に変換した部分を人が追えること」である。そのため、書き起こしの**どの行が原文のどこから来たか**、**何を補い、何を落としたか**を、必ず人が追える形で残す。

## 準備

- 道具は Python のパッケージ `mext` にある（依存ライブラリなし）。最初に `python3 -m mext.matcha_check --help` が動くかを確かめる。動かなければ、次のどちらかをする。
  - `pip install git+https://github.com/JRF-2018/mext` を実行する。
  - このスキルをプラグインとして入れた場合は、プラグインのルート（このスキルのディレクトリの 2 つ上）を `PYTHONPATH` に加える。
- 書く前に、次の二つを読む。
  - `references/writing_matcha.md`（このスキルのディレクトリ）: 文書を書き起こすときの考え方と型。
  - `../matcha-default-extensions/references/matcha_grammar.md`: Matcha / Matcha-D の文法。
- このスキルのファイルが手元にない場合（ほかの AI や、スキルを入れていない環境から頼まれた場合）は、https://github.com/JRF-2018/mext の `skills/matcha-analysis/` と `skills/matcha-default-extensions/references/` を読んで、同じ手順に従う。
- 引数: 文書のファイル（`.md` `.txt` など。以下 `X.md`）、または会話に貼られた文章。貼られた文章の場合は、まず `X.source.md` として保存し、利用者に名前の希望がなければ内容から短い名前 X を付ける。
- 出力は文書と同じディレクトリ（利用者が指定すればそこ）に置く: `X.matcha`、`X.matcha.md`。**原文のファイルは書き換えない**。

## 手順

### 1. 文書を読み、範囲を決める

- 文書の主な結論と、それを支える論証の筋を把握する。
- 文書に独立した論証が多い場合（目安: 主な結論が 4 つ以上、または 1 万字を超える文書）は、どこまで書き起こすかを決める。
  - 利用者に聞ける場合は聞く。選択肢の例: 「主な結論一つだけ」「主な結論すべて」「反論への応答も含めてすべて」。
  - 聞けない場合（非対話の実行など）は「主な結論すべて」にし、その旨を `X.matcha.md` の冒頭に書く。
- 文書が論証を含まない場合（純粋な記述、物語など）は、そのことを `X.matcha.md` に書いて終える。無理に書き起こさない。

### 2. 部品に分ける

`references/writing_matcha.md` §1 の表に従い、主張・根拠・要件・事実・評価・論点・例外・優先を拾い出す。

- 特に、「AだからB」の間に挟まっている**評価**を見つけて、`@評価` として表に出す。
- 文書が退けた反論も、主張として拾う（退け方に応じて `!` か `:: 優先` にする）。
- 文書が明示しない前提（隠れた前提）は、論証の筋に不可欠なものだけを補う。

### 3. `X.matcha` を書く

- `references/writing_matcha.md` §2 の型で書く。各主張に `as ラベル` を付ける。前の主張の結論を次の主張の要件にするときは、結論の文言を書き写さずに `$ラベル` で参照する（§2.7）。
- 文言に演算子の文字（`:` `@` `&` など）を入れない（§5）。
- ファイルの先頭に、次のコメントを書く。

  ```
  // 原文: X.md（題名や著者が分かれば書く）
  // matcha分析: AI（モデル名）による書き起こし。Matcha-D（!> / >> not / :: 優先、主張への as）は非公式の拡張。
  ```

- 各主張と各事実・評価の直前に `// 出典: 第N段落「短い引用」` を書く。
- 補った前提には `// 補った前提: 理由` を付ける。
- `::` と `//` の使い分け: `::` は原文の論証の構造（節立て）を写す見出しに使い、`//` は書き起こしの編集上の注記（出典、補った前提）に使う。道具はどちらのコメントの意味も読まない。**道具に読ませる判断（結び方、事実の種別など）はコメントに書かない**。それはメモに書き、mext分析で `.mext` の `[ai]` に移す（`references/writing_matcha.md` §3）。
- 成否の印（`+` / `!`）は、文書が成否を判断している場合だけ付ける。

### 4. 構文チェック（決定論的）

```bash
python3 -m mext.matcha_check --tree X.matcha
```

- エラーがなくなるまで直す。警告は、意図したものか確かめ、意図したものなら `X.matcha.md` に理由を書く。
- `--tree` の出力を見て、要件や結論が意図した要素につながっているかを確かめる（字下げの誤りは、エラーにならずに構造だけが変わることがある）。

### 4.5 事前の予測を書く（最初に解く前に）

形の点検で一度でも Extension を計算すると、その後の予測は「事前」の予測ではなくなる。そこで、構文チェックが通ったら、**解く前に**、原文を読んだ直感で、どの結論が成り立ち、どれが成り立たないと思うかを書く。メモ `X.matcha.md` をこの時点で作り、その「事前の予測」の節だけを先に書いておく（主要な結論ごとに、成り立つ／否定が成り立つ／決まらない、と一言の理由）。

予測の目的は、当てることではない。**AI の直観による読みと、形式化した構造が食い違う箇所を見つける**ことである。食い違いは、書き起こしの誤りか、原文の論証の飛躍か、直観の誤りのどれかのしるしであり、それ自体が発見になる。予測は後から書き換えない。

### 5. 形の点検と磨き上げ（決定論的な検査 → 書き直し）

書き起こしが文書の論証を写せているかを、決定論的な検査で確かめ、必要なら書き直す。

```bash
python3 -m mext init --solve X.matcha -o X.check.mext
python3 -m mext lint X.check.mext            # 書き起こしの粗さの検査
```

- 文書の主な結論が、少なくとも一つの Extension（文書が支持する側なら preferred Extension）に含まれるかを見る。含まれない場合は、原因が次のどちらかを判断する。
  - **書き起こしの誤り**（ラベルの付け忘れ、`!>` の向き、文言の不統一など）: `X.matcha` を直す。
  - **文書の論証そのものの穴**（要件を満たす事実が書かれていない、など）: `X.matcha` は直さずに、`X.matcha.md` に穴として書く。
- `lint` の警告を一つずつ見る。とくに次の二つは、書き起こしが粗いしるしである。
  - **同語反復の評価**: 評価の文言が要件の文言とほぼ同じなら、事実から要件への判断が一段にまとめられ、mext からは中身が見えない。原文がその間に置いている判断の段階（中間の要件、評価の理由）を書き分ける。原文が本当に一段で飛んでいるなら、それは原文の飛躍なので、書き分けずにメモに書く。
  - **一段の主張が多い**: 論証の中身が評価にまとめられていないかを見直す。
  - **行き止まりの主張**: 原文が結論の支えや限定として置いている主張が、結論とつながっていないことがある。原文がつないでいるなら `$ラベル`・`!>`・`:: 優先` でつなぐ。原文がつないでいないなら、それは原文の構造なので、メモに書く。
- **書き直すときの規律**:
  - 書き直す前に `python3 -m mext snapshot X.check.mext` で版を保存し、書き直した後に `python3 -m mext diff X.check.v1.mext X.check.mext` で比べる。
  - 書き直してよいのは、**原文への忠実さと粒度を上げるため**だけである（検査の警告、原文の読み直し、書き起こしの誤り）。**結論が出る・出ないを理由に書き直してはならない**。結論が出ないことが原文の穴によるなら、穴として残す。
  - 何を受けて何を直したかを、`X.matcha.md` の「改訂の記録」に書く（版ごとに一行以上。diff で結論の変化があれば、それも書く）。
  - 書き直しは、目安として 3 回までにする。それでも残る警告は、理由とともにメモに書く。
- この点検は書き起こしのためのもので、論証の審査ではない。点検が済んだら `X.check*.mext` と古い版の `.matcha` は、残して `X.matcha.md` から参照する（消さない。改訂の経緯を人が追えるように）。
- 形の点検で予測と食い違う結果が出ても、予測は直さない。食い違いはメモの「事前の予測」の節に追記する。

### 6. メモ `X.matcha.md` を書く

日本語で、次の章立てで書く。

```
# matcha分析: X

## 1. 文書の論証の要約      … 主な結論と、それを支える筋（数行）。書き起こした範囲
## 2. 対応表               … 原文の箇所（段落・引用）→ X.matcha の行番号とラベル。言い換えた場合はその旨
## 3. 書き起こしの判断      … 何を評価（@）としたか、何を例外（!>）・優先（:: 優先）としたか、その理由。
                           次の二つの表を含める（mext分析でこれを .mext の [ai] に移す）:
                           - 結び方: 二つ以上を並べた箇所ごとに、行・AND/OR・「明示」（原文に「すべて」「いずれか」
                             「以上から」などの手がかりがある）か「読み」（手がかりがなく、書き起こした者が読んだ）か。
                             手がかりがなければ「読み」と書けばよい。根拠を作らない
                           - 事実の種別: W に置いた事実ごとに、記述（原文が事実として述べる）・仮定（原文の仮定や思考実験）・
                             確認済み（原文の外で確かめた）・著者の主張（著者の評価や仮説が事実の形で書かれている）のどれか
## 4. 補った前提           … 一覧と、補った理由。補った前提は後の審査で最も疑われるべきものであることを明記する。
                           前提の文言（評価・要件・事実の文言）をそのまま書く（mext分析で [ai] の supplied に移す）
## 5. 落としたもの          … 書き起こさなかった部分と理由
## 6. 事前の予測           … 手順4.5 で、最初に解く前に書いた予測（書き換えない）。形の点検との食い違いの追記
## 7. 構文チェックと形の点検 … matcha_check と lint の結果（出力を貼る）、主な結論が Extension に出るか、見つけた論証の穴
## 8. 改訂の記録           … 版ごとに、何（lint の警告・読み直し・誤り）を受けて何を直したか、diff で見えた変化。改訂しなければ「なし」
## 9. 次の一歩             … mext分析（mext-analysis）に進むときの注意（同一視が必要になりそうな文言など）
```

### 7. 記録（最後に一度）

メモを書き終えたら、最後に一度だけ次を実行する。

```bash
python3 -m mext solve X.check.mext
```

これで `X.check.mext` のヘッダに、この時点の `X.matcha` と `X.matcha.md` のハッシュ値が記録される。後で人が書き起こしやメモを直したかどうかを、mext分析が `mext changed X.check.mext` で見分けるためである。この後は `X.check.mext` を解き直さない。

## 注意

- 会話への返答もファイルも、利用者の言語で書く（指定がなく判断できなければ日本語）。会話への返答は、最初の一文からその言語で書く。

- 書き起こしは解釈である。**原文にない主張を作らない**。原文の論証が弱いと思っても、強くして書き起こさない（弱さはそのまま写し、メモで指摘する）。
- 原文の文言を、論証の都合で書き換えない。縮める場合も意味を変えない。
- 法的な文書で条文・判例が引かれていれば `^根拠` に書く。引かれていなければ、あなたの知識で補わない（補うなら「補った前提」として明示する）。
