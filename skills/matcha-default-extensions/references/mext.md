# MEXT（Matcha EXTension notation）仕様

MEXT は、本パッケージで考案した、Matcha(-D) から得たデフォルト理論とその Extension を書くためのテキスト形式である。

設計原理は「機械的に変換した部分を人が追えること」で、そのためにファイルを三層に分ける。

1. **人・AI が書く層**: `[ai]`（判断）、`[extra]`（追加の知識）、`[claimed]`（検証したい Extension）
2. **決定論的に生成される層**: `[atoms]` `[W]` `[rules]` `[defaults]` `[priority]` `[extensions]` `[marks]` `[summary]`
3. **検証の層**: `mext verify`（主張された Extension の検証）、`mext lean`（Lean による証明）

生成される層は、Matcha ファイルと `[ai]` `[extra]` からいつでも再生成できる。`mext solve` を実行すると書き直される。

## 1. 論理

**リテラル型の命題デフォルト理論** (W, R, D, <) を使う。

- 原子命題 p と、その否定 ¬p（MEXT では `-p`）をリテラルと呼ぶ。
- W: 確定事実（リテラルの集合）。
- R: 確定規則 `l1 & … & lk -> l`。**推論規則**として扱い、対偶は取らない（法的推論の通例。PROLEG・ASP と同じ）。
- D: デフォルト `名前: 前提 : 正当化 / 結論`。前提はリテラルの連言、正当化はリテラルの並びで、**各リテラルが別々に**無矛盾であることを要求する。結論はリテラルの連言。
- <: デフォルト間の優先順位（`高 > 低`）。

**Extension**（Reiter 1980）: リテラル集合 E が Extension であるとは、E = Γ(E) となることをいう。ここで Γ(E) は次の条件を満たす最小の集合で、矛盾していれば全リテラルの集合とする。

- W を含む。
- R で閉じている。
- E に照らして正当化が無矛盾なデフォルト（各正当化 j について ¬j ∉ E）の前提が満たされれば、その結論を含む。

この理論は、Gelfond & Lifschitz (1991) の拡張論理プログラム（古典否定と失敗による否定を持つ）と一対一に対応する。デフォルト `a : b, c / h` は規則 `h ← a, not ¬b, not ¬c` に、Extension は解集合にそれぞれ対応する。

**計算法**: 正当化を無視して導出されうるリテラルの上界 P を求め、正当化の否定が P に入りうるデフォルト（「衝突しうるデフォルト」）を k 個とする。その部分集合 2^k 通りのそれぞれについて閉包を取り、E = Γ(E) を確かめる。それ以外のデフォルトは常に安全に適用できるので、この方法で Extension は漏れなく得られる。

**優先順位を尊重する生成（preferred Extension）**: Extension E が preferred であるとは、E の生成デフォルトを一つずつ適用していく列 g1, g2, … で、次の (i)(ii) を満たすものがあることをいう（Brewka & Eiter 1999 の考え方による、本パッケージの定義）。

- (i) **根拠づけ**: gi の前提は、W と g1…g(i−1) の結論の閉包 S に含まれる。
- (ii) **優先の尊重**: gi より優先されるデフォルト d が E の生成デフォルトでなく、しかも d の前提が（最終的な）E で満たされるなら、d はその時点の S ですでに打ち負かされていなければならない（d の正当化のどれかの否定が S に含まれる）。

優先順位は推移的に閉じる。(ii) で d の前提を S ではなく E で判定するのが要点である。これにより、例外の前提が評価デフォルトを経由して後から満たされる場合にも、例外の優先が効く（最初の試験で見つかった問題への対処）。

**判定の計算（0.5.4 以降）**: (i)(ii) の条件は、S が大きくなっても失われない（前提は S に残り、打ち負かされた d は打ち負かされたまま）。そのため、適用の順序は結果に効かない。適用できる生成デフォルトを適用できる限り適用する貪欲な閉包で、条件を満たす列があるかが決まる。0.5.3 までは列を深さ優先で探していたので、preferred でない Extension について指数的な時間がかかることがあった（答えは同じ）。

**懐疑的帰結と信憑的帰結**: 優先順位があるときは preferred Extension を、ないときはすべての Extension を対象にする。すべてで成り立つリテラルを懐疑的帰結、いずれかで成り立つリテラルを信憑的帰結とする。

## 2. Matcha(-D) からの変換規則（決定論的）

**基本方針**: 要件の構成（言い換え・AND・OR）は**必要十分条件**として読む。下位が成り立てば上位が成り立ち（`r ← 下位`）、AND の下位のどれか（OR なら全部）が否定されれば上位も否定される（`-r ← -下位`）。こうして「立証されていない」（E に含まれない）と「否定の根拠がある」（¬r が E に含まれる）を区別する。

| Matcha | 原子命題 | 規則・デフォルト |
|---|---|---|
| `<= 事実`（評価なし） | 事実 `f`（文言が同じなら同じ原子） | `f ∈ W` |
| `「要件」 <= 事実@評価` | 評価 `v`（「事実@評価」） | 評価デフォルト `e: f : v, r / v` と `r ↔ v`（評価は争いうるあてはめ。要件 r が否定されていれば評価は働かない） |
| `(事実 & 事実)@評価` | 補助原子 `x` と評価 `v` | `x ↔ f1 & f2`、`e: x : v, r / v` |
| `「要件」 <= 事実`（評価なし） | 要件 `r`（「主張名／要件」で区別） | `r ↔ f`（当然のあてはめ） |
| `「要件」: %定義 …` | `r`, `r'` | `r ↔ r'`（言い換え） |
| `( A & B )` / 改行の並び | 補助原子 `x` | `x ↔ A & B` |
| `( A \| B )` | 補助原子 `x` | `x ← A`、`x ← B`、`-x ← -A & -B` |
| `? 論点 ~> 理由 => %規範 : あてはめ` | 論点 `q`、理由 `y` | `q ↔ y & 規範 & あてはめ`。理由は事実ではなく論証の前提なので、W に入れずにデフォルト `⊤ : y / y` で受け入れる |
| 理由も規範もない `? 論点` | 論点 `q` | `⊤ : q / q` |
| `#主張 <= 対象: 要件… >> 結論 as d` | 主張 `k`、結論 `c`（「結論〔対象〕」） | 主張デフォルト `d: 対象 & 要件 : k, c / k, c` と `-k ← -要件` |
| `>> not 結論` / `>> !結論` | ¬c | 結論が `-c` になる |
| `X !> $d` | `ab(d)` | X の結論に `ab(d)` を加え、d の正当化に `-ab(d)` を加える。さらに `X > d` |
| `:: 優先 $a > $b` | — | `a > b` |
| 不成立（`!`）の要件の `<= 事実@評価` | — | `e: f : v, -r / v` と `-r ← v`（要件を満たさない根拠） |
| 不成立の主張の `>> 結論` | `c` | `d.不成立: ⊤ : -k, c / c` と、自動の優先順位 `d > d.不成立` |
| 成否の印 `+` / `!` | — | `[marks]` で照合する。`+` なら E に含まれること、`!` なら含まれないことを求める |

- **原子の区別と別名**:
  - 要件は「主張の名前／要件」で区別する。主張の名前は、ラベル（`as`）があればラベル、なければ主張名（重複すれば「 [位置]」付き）。主張の結論は「結論〔主張の対象〕」で区別する。別の主張に同じ文言の結論（「請求が認められる」など）があっても混ざらない。原則と例外のように対象が同じ主張どうしでは、同じ原子になる。
  - 主張は「#主張名^根拠」で表す。重複したときだけ「 [ラベル]」を付ける。
  - `[ai]` `[extra]` `[claimed]` と `explain` では、原子の文言のほか、別名でも指せる。別名にはラベル、`#主張名`、要件・結論の素の文言、neg / same を宣言する前の文言がある。複数の原子にあたる別名を使うと、候補を挙げて止まる。
- **不成立の主張**: 印 `!` が付いているか、印がなくても下位の AND に `!` がある（カント例）主張の結論は、「不成立からの帰結」と読む。著者が明示した `+` は推定より優先する。読み違えている場合は `[ai]` の `failure` / `effect` で正す。
- **参照 `$ラベル`**: 要件の位置に書いた `$ラベル` が**主張**を指すときは（主張の連鎖）、その主張と必要十分に結ぶ。主張が成り立てば要件が成り立ち（`r ← k`）、主張が否定されれば要件も否定される（`-r ← -k`）。**規範・定義**を指すとき（原典の用例 `=> %規範 as 名前` … `$名前 <= 別の事実`）は、同じ規範を別の事実にあてはめる意味なので結ばない（参照先のあてはめの結果を持ち込まない）。
- **`!` の伝播**: 言い換えだけの下位要件（`!%A: %B <= 事実`）の `%B` は、親の `!` を引き継ぐ。
- **例外 `!>`**: 「例外が勝つ」こと（優先順位）と「例外が働けば原則の正当化が崩れる」こと（`ab`）を同時に表す。例外の例外（`Y !> X`）によって X が働かなければ、原則は復活する。
- **新しい事実で別の Extension に移る**: 評価デフォルトの正当化には、あてはめ先の要件 r（または ¬r）が含まれる。そのため `[extra]` に反対の事実を足すと、評価が働かなくなるだけで、Extension が消えることはない。

## 3. ファイルの書式

```
@mext 1
theory: tweety.matcha            ; Matcha ファイル（MEXT ファイルからの相対パス）

[ai]                             ; AI（または人）の判断。; の後に理由を書く
same "代表の文言" "同じ意味の文言"
neg  "文言A" "文言B"              ; B は A の否定
failure "文言"                    ; 結論を「不成立からの帰結」と読む
effect  "文言"                    ; 結論を「成立の効果」と読む
review "事実@評価" ok|doubtful|reject   ; 評価の実質的妥当性（reject なら評価デフォルトを除く）

[extra]                          ; 追加の知識（背景知識・一般原則など）
fact "文言"
rule "a" & "b" -> -"c"
default 名前: "a" : "b" / "b"
priority 名前1 > 名前2

[claimed]                        ; 検証したい Extension（部分集合でよい）
E1*: "文言", -"文言", !"文言"     ; "X": X∈E、-"X": ¬X∈E、!"X": X∉E。* は preferred であることも主張する

; ===== ここから下は mext.py が自動生成（手で直さない） =====
[atoms]  [W]  [rules]  [defaults]  [priority]  [extensions]  [marks]  [summary]
```

**文言の書き方（0.5.0 以降）**: 文言は `"…"` で囲む。文言に `"` を含むとき（英文の `"要件"` を含む原子など）は、`'…'` で囲むか、`"…"` の中で `\"` と書く（`\` は `\\`）。`'…'` の中には `'` を書けないので、アポストロフィを含む文言（`the owner's offer`）は `"…"` で囲む。`[atoms]` は、`"` を含みアポストロフィを含まない文言を `'…'` で書き、両方を含むなら `\"` で書く。

- 原子の名前の接頭辞: `f` 事実、`r` 要件、`k` 主張、`c` 結論、`v` 評価、`x` 補助、`q` 論点、`y` 理由、`ab` 例外による阻却、`z` 追加。
- `options: no-review` をヘッダに書くと（`solve --no-review` で自動的に書かれる）、そのファイルでは `[ai]` の review を反映しない。これで、書かれたとおりの理論を `report` `explain` `verify` `lean` でも一貫して扱える。
- review は評価（`"事実@評価"`）のほか、評価のないあてはめにも使える。その場合は要件の文言（`"主張名／「要件」"` または素の文言）を指定する。reject すると、そのあてはめの規則を除く。
- `[ai]` と `[extra]` では、原子を名前ではなく**文言**で指す（名前は再生成で変わりうるため）。

## 4. 複数のファイルからなる理論

Matcha には import がないので、一つの理論を複数のファイルに分けて書く場合は、MEXT のヘッダに `theory:` を複数行書く（`mext init A.matcha B.matcha -o X.mext`）。

- 全ファイルを一つの理論として変換する。ラベルの名前空間は共有され、別ファイルの主張を `!> $ラベル` や `:: 優先` で指せる。
- 位置は「ファイル名:L12」で表示する。自動で付けるデフォルトの名前も「ファイル名.L12」の形になる。
- 構文チェックは `matcha-check --shared-labels A.matcha B.matcha` で行う（単独で検査すると、別ファイルのラベルは未定義のエラーになる）。

## 5. コマンド

**出力の言語（0.4.0 以降）**: 既定は日本語。`--lang en` を付けるか、環境変数 `MEXT_LANG=en` にすると、すべてのコマンドの出力（構文チェッカの診断、生成部分のコメント、report・summary・sensitivity など）が英語になる。生成部分の区切りの行も `; ===== generated by mext below this line (do not edit) =====` になる（どちらの区切りも読める）。`[ai]` の語彙は英語でも書ける: `connective … explicit|reading`、`fact-kind … description|assumption|verified|author-claim`。

**手順の点検（audit、0.4.0 以降）**: `mext audit X.mext` は、分析の手順の抜けを ✓ / ✗ / － で一覧にする（書き起こしの記録とその後の変更、メモ、構文と lint の警告、効いていない [ai]、未審査の評価、事実の種別、結論を左右する結び方の記録、補った前提、予測とその検証、出力のファイル）。✗ があれば終了コード 1。


```
mext init       X.matcha [Y.matcha …] [-o X.mext] [--solve]
                                    # ひな形 X.mext を作る。複数のファイルは一つの理論にまとめる（--solve で求解も行う）
mext solve      X.mext [--no-review]
mext verify     X.mext [--skeptical] # [claimed] を検証（既定は信憑的: いずれかの Extension で成り立つ。
                                    #   --skeptical: すべての Extension で成り立つ）
mext report     X.mext              # Markdown の表
mext explain    X.mext E1 "文言"     # 導出のすべての根拠。含まれない場合は含まれない理由（否定は ¬文言）
mext lean       X.mext              # 各 Extension が Γ(E)=E を満たすことの Lean 証明
```

分析のコマンド（0.3.0 以降。いずれも決定論的）:

```
mext connectives X.mext [-o 出力.md]
                                    # 結び方の感度（0.3.3 以降）: AND / OR を一つずつ入れ替えたときの帰結と依存の変化
mext changed X.mext                 # この .mext を最後に init / solve した後に、.matcha や書き起こしのメモが変わったか
mext summary X.mext [-o 出力.md]    # 一画面の要約（0.3.1 以降）: 最終的な結論ごとの成否・対立する命題・決め手になる前提、検証の範囲、争点
mext sensitivity X.mext [--target "文言"] [--size auto|N] [--facts] [--full] [-o 出力.md]
                                    # 感度分析。結論ごとに、外すと成り立たなくなる前提を一覧にする
mext lint    X.mext                 # 書き起こしの粗さの検査
mext snapshot X.mext [--tag v1]     # X.matcha と X.mext を X.v1.matcha・X.v1.mext として保存する
mext diff    X.v1.mext X.mext [--all] [--no-sensitivity]
                                    # 二つの版の、帰結・Extension・評価・審査・依存の差
mext compare --init A.mext B.mext [-o A.vs.B.compare]
mext compare A.vs.B.compare [-o 出力.md]      # 読みの比較（0.5.0 以降）: 同じ文書の二つの書き起こしの、結論ごとの成否と依存の違い
mext compare A.mext B.mext [-m A.vs.B.compare]
```

**感度分析（sensitivity）**: 争いうる前提を外した理論の Extension を計算し直す。外す候補は、評価・論点・理由・`[extra]` のデフォルト、主張（その規範を採らないこと）、`[extra]` で足した事実である（`--facts` で Matcha の事実も加える）。外した評価は、`review reject` と同じ扱いになる。結論ごとに次を示す。「成り立つ」は、すべての preferred Extension に含まれること（懐疑的帰結）である。一部の preferred Extension でだけ成り立つ結論（0.5.1 以降）は、成り立つ preferred Extension が一つもなくなることを「成り立たなくなる」と数える（その結論が成り立つ読みの中での依存）。懐疑的に成り立つ結論で、単独で外すとすべての preferred Extension には入らなくなるが一部には残る前提には、〔一部の Extension には残る〕と印を付ける（0.5.3 以降。浮動する結論の片方の経路など）。`--full` は、組を省略せずにすべて示す。

- 単独で外すと成り立たなくなる前提
- 組で外すと成り立たなくなる極小の組（`--size` まで）。同じ結論への独立した経路が複数あるときに現れる
- 外すと否定が成り立つ前提
- 極小の支持の組の一例（候補を順に、外せるだけ外して、なお結論が残る組）
- AI が doubtful とした評価のうち、どの結論が依存しているか
- 外すと新たに成り立つ結論（デフォルト論理は非単調なので、前提を外すと、それが打ち消していた結論が現れることがある）

**結び方の感度（connectives）と、結び方・事実の種別の記録（0.3.3 以降）**:

- `mext connectives` は、二つ以上を並べた箇所（AND / OR の組）を一つずつ入れ替えて理論を作り直し、懐疑的帰結（結論・主張）の変化と、最終的な結論の依存（単独で外すと成り立たなくなる前提）の変化を示す。結び方は、どれかの前提が崩れたときに効いてくるので、帰結が同じでも依存の数が変わる（AND → OR で減り、OR → AND で増える）。
- `[ai]` の `connective "主張のラベルか要件の文言（または L行番号）" 明示|読み ; 理由` で、結び方が原文に明示されているか、書いた者の読みかを記録する。手がかりがなければ `読み` でよく、根拠を作る必要はない。connectives と summary は、結論を左右する結び方のうち、明示・読み・未記録の数を示す。明示のない結び方が結論を左右しているなら、結論から逆算した結び方でないかを、原文に照らして確かめる。
- `[ai]` の `fact-kind "事実の文言" 記述|仮定|確認済み|著者の主張 ; 理由` で、W の事実の種別を記録する。検証の範囲に種別の内訳を出し、`仮定` と `著者の主張` は感度分析で外す候補にする。

**補った前提（0.3.5 以降。`[ai]` の `supplied`）**: `supplied "前提の文言" … ; 理由` で、原文になく書き起こした者が補った前提を記録する。評価・主張・事実の文言、ラベル、または要件の文言で指す（要件の文言なら、その要件へのあてはめの評価に印が付く）。補った事実は、感度分析で外す候補になる。summary は、最終的な結論の決め手（単独で外すと成り立たなくなる前提）や「複数の経路に共通する判断」が補った前提であれば、「原文にない前提（書き起こした者が補ったもの）に依存する」と知らせる。そうした結論は、原文の論証の強さではなく、書き起こしの選択の結果である可能性がある。検証の範囲に、補った前提の数を出す。

**変更の記録（0.3.3 以降）**: `init` と `solve` は、`.mext` のヘッダに、元の `.matcha` と、同じ場所にあれば書き起こしのメモ（`X.matcha.md`）のハッシュ値を `source: ファイル sha256=…` として書く。`mext changed X.mext` は、記録の時点から変わったか（変わっていない・変わった・見つからない・記録の後にできた）を示す。タイムスタンプは、コピーや git の操作で中身と関係なく変わるので使わない。

**争点の共有と独立（0.3.2 以降。`[ai]` の `concern` と `distinct`）**: mext は原子の構造しか見ないので、内容の似た前提も別の原子として数える。そのため、同じ結論を支える経路が三本あっても、それが「独立した三つの根拠」なのか「同じ弱点を共有する三つの言い換え」なのかは、計算からは分からない。この判断は AI（または人）が `[ai]` に書く。

```
concern 名 "前提の文言" "前提の文言" …   ; 理由   … これらは内容の上で一つの争点を共有する
distinct "前提の文言" "前提の文言" …     ; 理由   … これらは内容の上で互いに独立である
```

前提の文言は、評価の文言（`"事実@評価"`）、主張のラベル、デフォルトの名前、感度分析の候補 ID のどれでもよい。感度分析は、`concern` の前提をまとめて一つの単位として外した場合も計算する。独立した経路から一つずつ外す形の組には、次のどれかを添える。

- `concern` がすべての経路にかかる: 「経路は複数でも、内容の上の弱点は一つ。この争点一つを崩すと、すべての経路が同時に崩れる」
- `distinct` がすべての経路の要にかかる: 「経路は互いに補い合う独立した根拠である」
- どちらもない: 「経路が内容の上でも独立かは、AI が判断していない」

**判断ごとと、あてはめ一か所（0.3.4 以降）**: 同じ評価（`事実@評価` の文言）が複数の箇所であてはめられていると、評価の原子は一つで、それを複数のデフォルトが支える。このとき感度分析は、「評価（判断ごと）」（原子を支えるデフォルトすべてを外す。`review reject` と同じで、その判断を採らないこと）と、「評価（あてはめ一か所）」（デフォルトを一つだけ外す。経路を一つ外すこと）を別の候補にする。あてはめを一か所ずつ外しても結論が残るのに、判断ごと外すと消えるなら、その判断は複数の経路に共通する弱点であり、sensitivity と summary の「複数の経路に共通する判断」に挙げる。同じ文言の評価を使えば、`concern` を書かなくても、共通の判断として扱われる。

**単独で必要な前提と、組の一員の区別**: AI が doubtful とした評価の一覧と summary の争点では、「単独で外すと成り立たなくなる」前提と、「組の一員（これ一つを外しても残るが、これを含む組を外すと成り立たなくなる）」前提を分けて示す。

**調べる範囲**: 既定の `--size auto` では、全候補で大きさ 2 までの組を調べる（候補が 80 個を超えれば大きさ 1 まで）。そこで依存が見つからない結論については、支持の組（なお結論が残る、候補の極小の組）を集めながら、そのすべてと交わる組を大きさ 4 まで調べる（同じ結論を独立した経路が支えている場合、各経路から一つずつ外して初めて結論が消える）。各経路から一つずつ外す形の組は、「独立した 3 つの経路から一つずつ: {…} × {…} × {…}」のようにまとめて示す。表の「調べた範囲」の列に、結論ごとに調べた範囲を書く。「—」は調べた範囲で見つからなかったことを表し、より大きな組で効く可能性は残る。`--size N` を与えると、全候補で大きさ N まで調べる（自動の拡張はしない）。

結論を直接導く唯一の主張（それ一つを外せば結論が消える、自明な場合）は、経路の探索では固定して残す。

依存する候補のない結論は、W の事実と規則だけから出ているか、反論が立証されていないこと（不成立からの帰結）から出ている。`^根拠` は表示であって、独立に立証される前提ではないので、候補には入らない。

**検証の範囲**（0.3.1 以降。`solve` の画面、生成部分の `[summary]`、`report`、`summary` に出す）: 結果の見栄えが、実際に検証した範囲より強く見えないようにするための数である。

- 評価の審査の内訳（未審査・ok・doubtful・reject）。doubtful と未審査の評価も、推論を止めない。
- 最終的な結論（主張の結論で、その結論も主張自体も、ほかのデフォルトや規則の前提に使われていないもの）の数と、そのうち成り立つもの、**理論の中に対立する命題（否定を結論とするデフォルトか規則）がないもの**の数。対立する命題のない結論は、反対の根拠に勝ったのではなく、反対の根拠が書かれていないだけである。

**一画面の要約（summary）**: 最終的な結論ごとに、成否、対立する命題の有無、決め手になる争いうる前提（単独で外すと成り立たなくなる前提。doubtful と未審査に印を付ける）、注意（独立した経路、反対の根拠がないことなど）を一つの表にし、最終的な結論が依存している doubtful・未審査の評価を「争点」として挙げる。全表と全導出（report、sensitivity、explain）は監査のために残し、summary をその入口にする。

**書き起こしの検査（lint）**: 決定論的な目安で、警告があっても誤りとは限らない。

| 項目 | 種類 | 内容 |
|---|---|---|
| 同語反復の評価 | 警告 | `<= 事実@評価` の評価が、あてはめ先の要件とほぼ同じ文言。判断が一段にまとめられ、mext から中身が見えない |
| 結論の文言の書き写し | 警告 | 事実も下位の要件もない要件が、ほかの主張の結論と同じ文言。`$ラベル` で参照すべき |
| 立証の手段のない要件 | 警告 | 事実（`<=`）も下位の要件（`:`）もない要件。これを含む主張は働かない |
| 効いていない判断 | 警告 | `[ai]` の文言が理論のどこにも当たらない。評価なら、同じ「@評価」の原子を候補として示す |
| 一段の主張が多い | 情報 | 主張の 7 割以上が、要件一つ・評価一つ以下 |
| 行き止まりの主張 | 情報 | 結論がどこにも使われていない主張が二つ以上ある（最終的な結論のほかに、結論に効いていない主張がある） |
| 事実の中の評価語 | 情報 | 事実に「べき」「すぎない」「当然」などの評価の語がある |
| どの Extension にも出ない主張 | 情報 | 著者が `!` を付けていないのに、どの Extension にも含まれない主張 |
| 評価に依存する報告 | 情報 | 報告の形の結論（「前者では…と説明する」）の主張が評価を要件にしている（0.5.2 以降）。評価を外すと報告まで消える。報告の主張と、それを `$ラベル` で受けて評価する主張に分ける |
| 原文に見当たらない引用 | 情報 | `// 出典:`（`// Source:`）の注の「…」の引用が、`// 原文:` のファイルに見当たらない（0.5.6 以降。`…` で区切った引用は断片ごとに探し、空白・句読点・括弧の違いは無視する。段落番号は確かめない） |
| 報告型の結論 | 情報 | 結論が「…と説明する」「著者は…と考える」のような立場の報告の形で、`$ラベル` で受けられていないものが二つ以上あり、理論に対立する命題がないか、そうした結論が主張の 3 割以上（0.5.0 以降）。報告どうしは両立するので、原文が両立しないとする立場も対立しない |

**版の差分（diff）**: 原子を番号ではなく文言で対応づける。書き起こしを直すと原子の番号や行番号がずれるので、普通の diff では論証の変化が読めない。そのため、次を比べる。

- 懐疑的帰結の変化（否定に転じたもの、成り立たなくなったもの、新たに成り立つもの）
- Extension の数
- 原子（結論・主張・評価・要件）の増減と、評価に実際に効いた審査
- 優先順位
- 依存の変化（両方の版で成り立つ結論について、単独で外すと成り立たなくなる前提の変化）
- `[ai]` の行の増減と、新しい版で効いていない `[ai]` の判断

**読みの比較（compare。0.5.0 以降）**: 同じ文書を別々に書き起こした二つの MEXT を比べる。diff と違い、原子の文言が大きく違う（言語が違うこともある）読みどうしを比べるので、どの結論・前提が対応するかを AI（または人）が比較のファイルに書く。

```
@mext-compare 1
a: A/killing.mext                 ; 比較のファイルからの相対パス
b: B/article.mext

[match]
match "A の結論の文言" "B の結論の文言"   ; 理由（同じ命題か。強さや対象の違いも書く）
match "@A の評価" "@B の評価"             ; 前提どうしも対応づけられる（同じ判断）
```

- 文言は `[ai]` と同じく、原子の文言、〔対象〕を除いた文言、ラベル、`#主張名`、`"@評価"` で指せる。ラベルや `#主張名` で指すと、その主張の結論どうしを比べる。
- 〔対象〕を除いて文言が同じ最終的な結論と、文言が同じ前提（感度分析の候補）は、自動で対応づける。`--init` のひな形には、対応のない最終的な結論と、文言の近い組（文字の一致の割合による機械的な候補）を注として書く。
- 出力: §1 全体（原子・規則・主張・Extension・評価の審査・補った前提・最終的な結論・対立する命題のない結論・lint の数を並べる）、§2 対応する結論（成否、決め手、共通の決め手、違い）、§3 対応のない最終的な結論、§4 対応する前提（審査と、決め手にしている結論の数）、§5 解決できなかった `[match]` の行。
- `match "A" "B" 関係 ; 理由` の関係（任意。`同じ`・`強さ`・`報告と主張`・`対象`、英語では `same`・`strength`・`report-claim`・`target`）は、理由の頭に示し、関係ごとの数を数える（0.5.3 以降）。
- 「違い」の列は、一方の読みでだけ中間の結論であること（0.5.3 以降）、成否の違い、preferred Extension が分かれること、補った前提・doubtful の評価・明示のない結び方に依存するのが一方だけであること、決め手の有無、独立した経路の数の違いを示す。
- どちらの読みが正しいかは示さない。違いが書き起こしの誤りか、粒度の違いか、判断の違いか、原文の曖昧さかは、原文に照らして判断する（スキル mext-compare）。

Lean 出力は、Γ を Lean の関数として定義し、`decide +kernel` で `isExtension T E = true` を示す。

- `--import-spec` を付けると、検査器を自前で定義せずに `lean/MextSpec.lean` を import する。そのうえで、健全性定理 `Mext.isExtension_sound` によって `Mext.ReiterExtension T E` まで示す。
  - `ReiterExtension T E` は、E が無矛盾で、W を含み、規則と「正当化が E と無矛盾なデフォルト」とで閉じた集合のうち最小である、という Reiter の定義である。
  - 健全性定理は、反復回数（規則の数 + デフォルトの数 + 1）で Γ の不動点に達することの証明を含む。
  - 依存する公理は Lean の標準の 3 つ（propext、Classical.choice、Quot.sound）だけである。
- これで示せるのは、列挙された各集合が Extension であること（健全性）である。列挙が漏れなくなされていること（完全性）は、`mext` のアルゴリズムに依存する。
