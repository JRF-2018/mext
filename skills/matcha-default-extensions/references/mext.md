# MEXT（Matcha EXTension notation）仕様

MEXT は、本パッケージで考案した、Matcha(-D) から得たデフォルト理論とその Extension を書くためのテキスト形式である。

設計原理は「機械的に変換した部分を人が追えること」で、そのためにファイルを三層に分ける。

1. **人・AI が書く層**: `[ai]`（判断）、`[extra]`（追加の知識）、`[claimed]`（検証したい Extension）
2. **決定論的に生成される層**: `[atoms]` `[W]` `[rules]` `[defaults]` `[priority]` `[extensions]` `[marks]` `[summary]`
3. **検証の層**: `mext.py verify`（主張された Extension の検証）、`mext.py lean`（Lean による証明）

生成される層は、Matcha ファイルと `[ai]` `[extra]` からいつでも再生成できる。`mext.py solve` を実行すると書き直される。

## 1. 論理

**リテラル型の命題デフォルト理論** (W, R, D, <) を使う。

- 原子命題 p と、その否定 ¬p（MEXT では `-p`）をリテラルと呼ぶ。
- W: 確定事実（リテラルの集合）。
- R: 確定規則 `l1 & … & lk -> l`。**推論規則**として扱い、対偶は取らない（法的推論の通例。PROLEG・ASP と同じ）。
- D: デフォルト `名前: 前提 : 正当化 / 結論`。前提はリテラルの連言、正当化はリテラルの並びで、**各リテラルが別々に**無矛盾であることを要求する。結論はリテラルの連言。
- <: デフォルト間の優先順位（`高 > 低`）。

**Extension**（Reiter 1980）: リテラル集合 E が Extension であるとは、E = Γ(E) となることをいう。ここで Γ(E) は次の条件を満たす最小の集合で、矛盾していれば全リテラルの集合とする。

- W を含む。
- R で閉じている。
- E に照らして正当化が無矛盾なデフォルト（各正当化 j について ¬j ∉ E）の前提が満たされれば、その結論を含む。

この理論は、Gelfond & Lifschitz (1991) の拡張論理プログラム（古典否定と失敗による否定を持つ）と一対一に対応する。デフォルト `a : b, c / h` は規則 `h ← a, not ¬b, not ¬c` に、Extension は解集合にそれぞれ対応する。

**計算法**: 正当化を無視して導出されうるリテラルの上界 P を求め、正当化の否定が P に入りうるデフォルト（「衝突しうるデフォルト」）を k 個とする。その部分集合 2^k 通りのそれぞれについて閉包を取り、E = Γ(E) を確かめる。それ以外のデフォルトは常に安全に適用できるので、この方法で Extension は漏れなく得られる。

**優先順位を尊重する生成（preferred Extension）**: Extension E が preferred であるとは、E の生成デフォルトを一つずつ適用していく列 g1, g2, … で、次の (i)(ii) を満たすものがあることをいう（Brewka & Eiter 1999 の考え方による、本パッケージの定義）。

- (i) **根拠づけ**: gi の前提は、W と g1…g(i−1) の結論の閉包 S に含まれる。
- (ii) **優先の尊重**: gi より優先されるデフォルト d が E の生成デフォルトでなく、しかも d の前提が（最終的な）E で満たされるなら、d はその時点の S ですでに打ち負かされていなければならない（d の正当化のどれかの否定が S に含まれる）。

優先順位は推移的に閉じる。(ii) で d の前提を S ではなく E で判定するのが要点である。これにより、例外の前提が評価デフォルトを経由して後から満たされる場合にも、例外の優先が効く（最初の試験で見つかった問題への対処）。

**懐疑的帰結と信憑的帰結**: 優先順位があるときは preferred Extension を、ないときはすべての Extension を対象にする。すべてで成り立つリテラルを懐疑的帰結、いずれかで成り立つリテラルを信憑的帰結とする。

## 2. Matcha(-D) からの変換規則（決定論的）

**基本方針**: 要件の構成（言い換え・AND・OR）は**必要十分条件**として読む。下位が成り立てば上位が成り立ち（`r ← 下位`）、AND の下位のどれか（OR なら全部）が否定されれば上位も否定される（`-r ← -下位`）。こうして「立証されていない」（E に含まれない）と「否定の根拠がある」（¬r が E に含まれる）を区別する。

| Matcha | 原子命題 | 規則・デフォルト |
|---|---|---|
| `<= 事実`（評価なし） | 事実 `f`（文言が同じなら同じ原子） | `f ∈ W` |
| `「要件」 <= 事実@評価` | 評価 `v`（「事実@評価」） | 評価デフォルト `e: f : v, r / v` と `r ↔ v`（評価は争いうるあてはめ。要件 r が否定されていれば評価は働かない） |
| `(事実 & 事実)@評価` | 補助原子 `x` と評価 `v` | `x ↔ f1 & f2`、`e: x : v, r / v` |
| `「要件」 <= 事実`（評価なし） | 要件 `r`（「主張名／要件」で区別） | `r ↔ f`（当然のあてはめ） |
| `「要件」: %定義 …` | `r`, `r'` | `r ↔ r'`（言い換え） |
| `( A & B )` / 改行の並び | 補助原子 `x` | `x ↔ A & B` |
| `( A \| B )` | 補助原子 `x` | `x ← A`、`x ← B`、`-x ← -A & -B` |
| `? 論点 ~> 理由 => %規範 : あてはめ` | 論点 `q`、理由 `y` | `q ↔ y & 規範 & あてはめ`。理由は事実ではなく論証の前提なので、W に入れずにデフォルト `⊤ : y / y` で受け入れる |
| 理由も規範もない `? 論点` | 論点 `q` | `⊤ : q / q` |
| `#主張 <= 対象: 要件… >> 結論 as d` | 主張 `k`、結論 `c`（「結論〔対象〕」） | 主張デフォルト `d: 対象 & 要件 : k, c / k, c` と `-k ← -要件` |
| `>> not 結論` / `>> !結論` | ¬c | 結論が `-c` になる |
| `X !> $d` | `ab(d)` | X の結論に `ab(d)` を加え、d の正当化に `-ab(d)` を加える。さらに `X > d` |
| `:: 優先 $a > $b` | — | `a > b` |
| 不成立（`!`）の要件の `<= 事実@評価` | — | `e: f : v, -r / v` と `-r ← v`（要件を満たさない根拠） |
| 不成立の主張の `>> 結論` | `c` | `d.不成立: ⊤ : -k, c / c` と、自動の優先順位 `d > d.不成立` |
| 成否の印 `+` / `!` | — | `[marks]` で照合する。`+` なら E に含まれること、`!` なら含まれないことを求める |

- **原子の区別と別名**:
  - 要件は「主張の名前／要件」で区別する。主張の名前は、ラベル（`as`）があればラベル、なければ主張名（重複すれば「 [位置]」付き）。主張の結論は「結論〔主張の対象〕」で区別する。別の主張に同じ文言の結論（「請求が認められる」など）があっても混ざらない。原則と例外のように対象が同じ主張どうしでは、同じ原子になる。
  - 主張は「#主張名^根拠」で表す。重複したときだけ「 [ラベル]」を付ける。
  - `[ai]` `[extra]` `[claimed]` と `explain` では、原子の文言のほか、別名でも指せる。別名にはラベル、`#主張名`、要件・結論の素の文言、neg / same を宣言する前の文言がある。複数の原子にあたる別名を使うと、候補を挙げて止まる。
- **不成立の主張**: 印 `!` が付いているか、印がなくても下位の AND に `!` がある（カント例）主張の結論は、「不成立からの帰結」と読む。著者が明示した `+` は推定より優先する。読み違えている場合は `[ai]` の `failure` / `effect` で正す。
- **参照 `$ラベル`**: 要件の位置に書いた `$ラベル` が**主張**を指すときは（主張の連鎖）、その主張と必要十分に結ぶ。主張が成り立てば要件が成り立ち（`r ← k`）、主張が否定されれば要件も否定される（`-r ← -k`）。**規範・定義**を指すとき（原典の用例 `=> %規範 as 名前` … `$名前 <= 別の事実`）は、同じ規範を別の事実にあてはめる意味なので結ばない（参照先のあてはめの結果を持ち込まない）。
- **`!` の伝播**: 言い換えだけの下位要件（`!%A: %B <= 事実`）の `%B` は、親の `!` を引き継ぐ。
- **例外 `!>`**: 「例外が勝つ」こと（優先順位）と「例外が働けば原則の正当化が崩れる」こと（`ab`）を同時に表す。例外の例外（`Y !> X`）によって X が働かなければ、原則は復活する。
- **新しい事実で別の Extension に移る**: 評価デフォルトの正当化には、あてはめ先の要件 r（または ¬r）が含まれる。そのため `[extra]` に反対の事実を足すと、評価が働かなくなるだけで、Extension が消えることはない。

## 3. ファイルの書式

```
@mext 1
theory: tweety.matcha            ; Matcha ファイル（MEXT ファイルからの相対パス）

[ai]                             ; AI（または人）の判断。; の後に理由を書く
same "代表の文言" "同じ意味の文言"
neg  "文言A" "文言B"              ; B は A の否定
failure "文言"                    ; 結論を「不成立からの帰結」と読む
effect  "文言"                    ; 結論を「成立の効果」と読む
review "事実@評価" ok|doubtful|reject   ; 評価の実質的妥当性（reject なら評価デフォルトを除く）

[extra]                          ; 追加の知識（背景知識・一般原則など）
fact "文言"
rule "a" & "b" -> -"c"
default 名前: "a" : "b" / "b"
priority 名前1 > 名前2

[claimed]                        ; 検証したい Extension（部分集合でよい）
E1*: "文言", -"文言", !"文言"     ; "X": X∈E、-"X": ¬X∈E、!"X": X∉E。* は preferred であることも主張する

; ===== ここから下は mext.py が自動生成（手で直さない） =====
[atoms]  [W]  [rules]  [defaults]  [priority]  [extensions]  [marks]  [summary]
```

- 原子の名前の接頭辞: `f` 事実、`r` 要件、`k` 主張、`c` 結論、`v` 評価、`x` 補助、`q` 論点、`y` 理由、`ab` 例外による阻却、`z` 追加。
- `options: no-review` をヘッダに書くと（`solve --no-review` で自動的に書かれる）、そのファイルでは `[ai]` の review を反映しない。これで、書かれたとおりの理論を `report` `explain` `verify` `lean` でも一貫して扱える。
- review は評価（`"事実@評価"`）のほか、評価のないあてはめにも使える。その場合は要件の文言（`"主張名／「要件」"` または素の文言）を指定する。reject すると、そのあてはめの規則を除く。
- `[ai]` と `[extra]` では、原子を名前ではなく**文言**で指す（名前は再生成で変わりうるため）。

## 4. 複数のファイルからなる理論

Matcha には import がないので、一つの理論を複数のファイルに分けて書く場合は、MEXT のヘッダに `theory:` を複数行書く（`mext.py init A.matcha B.matcha -o X.mext`）。

- 全ファイルを一つの理論として変換する。ラベルの名前空間は共有され、別ファイルの主張を `!> $ラベル` や `:: 優先` で指せる。
- 位置は「ファイル名:L12」で表示する。自動で付けるデフォルトの名前も「ファイル名.L12」の形になる。
- 構文チェックは `matcha_check.py --shared-labels A.matcha B.matcha` で行う（単独で検査すると、別ファイルのラベルは未定義のエラーになる）。

## 5. コマンド

```
mext.py init    X.matcha [Y.matcha …] [-o X.mext] [--solve]
                                    # ひな形 X.mext を作る。複数のファイルは一つの理論にまとめる（--solve で求解も行う）
mext.py solve   X.mext [--no-review]
mext.py verify  X.mext [--skeptical] # [claimed] を検証（既定は信憑的: いずれかの Extension で成り立つ。
                                    #   --skeptical: すべての Extension で成り立つ）
mext.py report  X.mext              # Markdown の表
mext.py explain X.mext E1 "文言"     # 導出のすべての根拠。含まれない場合は含まれない理由（否定は ¬文言）
mext.py lean    X.mext              # 各 Extension が Γ(E)=E を満たすことの Lean 証明
```

Lean 出力は、Γ を Lean の関数として定義し、`decide +kernel` で `isExtension T E = true` を示す。

- `--import-spec` を付けると、検査器を自前で定義せずに `WallersteinTheory/MextSpec.lean` を import する。そのうえで、健全性定理 `Mext.isExtension_sound` によって `Mext.ReiterExtension T E` まで示す。
  - `ReiterExtension T E` は、E が無矛盾で、W を含み、規則と「正当化が E と無矛盾なデフォルト」とで閉じた集合のうち最小である、という Reiter の定義である。
  - 健全性定理は、反復回数（規則の数 + デフォルトの数 + 1）で Γ の不動点に達することの証明を含む。
  - 依存する公理は Lean の標準の 3 つ（propext、Classical.choice、Quot.sound）だけである。
- これで示せるのは、列挙された各集合が Extension であること（健全性）である。列挙が漏れなくなされていること（完全性）は、`mext.py` のアルゴリズムに依存する。
