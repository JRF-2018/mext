# AI の判断の書き方（MEXT の `[ai]` `[extra]` `[claimed]`）

AI（または人）の判断は、すべて `.mext` の `[ai]` `[extra]` `[claimed]` 節に、一行ずつ `; 理由` を付けて書く。生成部分（`; ===== ここから下は mext.py が自動生成` 以下）は手で直さない。**確信のない判断は書かない**（迷うものはレポートの「保留した判断」に挙げる）。

文言は `[atoms]` の `"…"` をそのまま写すほか、別名（ラベル、`#主張名`、要件や結論の素の文言、評価の部分だけの `"@評価"`）でも指せる。`"@評価"` は、同じ評価の文言を持つすべての評価に効く。複数の原子にあたる別名を使うと mext が候補を示すので、原子の文言で書き直す。

## `[ai]` の判断

| 判断 | 書き方 | いつ書くか |
|---|---|---|
| 同一 | `same "代表" "別名"` | 文言は違うが同じ命題を指すとき。別の主張の中で根拠なしに繰り返された要件には、ほぼ必ず要る（`[marks]` の「不一致」が手がかり） |
| 否定 | `neg "A" "B"` | B が A の否定のとき（「同意している」と「同意していない」など）。`>> not` で明示された否定には不要 |
| 結論の型 | `failure "文言"` / `effect "文言"` | `>>` の結論が「成立の効果」か「不成立からの帰結」かの既定の読み（著者の印 `!` からの推定）が誤っているときだけ |
| あてはめの審査 | `review "対象" ok\|doubtful\|reject` | 評価（`"事実@評価"`）か、評価のないあてはめの要件の文言について。ok: 通常の評価として成り立つ。doubtful: 争いうる（誤記の疑いも）。reject: 明らかな飛躍だけ（理由を具体的に） |
| 争点の共有と独立 | `concern 名 "前提" …` / `distinct "前提" …` | 感度分析で「独立した N つの経路」が出たとき、経路の要の前提が一つの争点を共有するか、互いに独立か。判断できなければ書かない |
| 結び方 | `connective "主張のラベルか要件の文言" 明示\|読み` | AND / OR が原文に明示されているか（「すべて」「いずれか」「以上から」など）、書いた者の読みか。手がかりがなければ「読み」でよい。**根拠を作らない** |
| 事実の種別 | `fact-kind "事実の文言" 記述\|仮定\|確認済み\|著者の主張` | W の事実が、原文の記述か、仮定・思考実験か、原文の外で確かめたことか、著者の評価や仮説が事実の形で書かれたものか |
| 補った前提 | `supplied "前提の文言" …` | 原文になく、書き起こした者が補った前提。評価・主張・事実・要件の文言で指す |

審査の補足:

- `A@占有者` のように人や物を評価して要件上の役割に当てる書き方は、Matcha の通常の書き方である。役割の割り当てが事実で支えられているかを審査する。
- 反対の事情が支持の根拠と同じ AND に並んでいる、事実どうしが食い違う、などの構造の問題は、`doubtful` にしてレポートで述べる。
- 書き起こした本人として甘くならない。`@評価` として表に出した判断と、補った前提こそが、弱点の候補である。

行の注には、判断の出どころを書く。メモから移したものは `; 書き起こしの判断（X.matcha.md §3）: …`、審査で改めたものは `; 審査で改めた: …`。

## `[extra]` の背景知識

足さなければ論証が成り立たない場合、または著者の根拠が結論につながっていない場合だけ、`fact` / `rule` / `default` / `priority` を `; 理由` 付きで書く。足した知識はレポートで明示する。新しい事実を例外として扱うには、`default 名: "前提" : -"原則の結論" / -"原則の結論"` と `priority 名 > 原則のラベル` を組み合わせる。

## `[claimed]` の予測

```
E1*: "主要な結論", -"否定される結論", !"成り立たない主張"   ; 予測の理由
```

- `"X"` は X ∈ E、`-"X"` は ¬X ∈ E、`!"X"` は X ∉ E。`*` は preferred であることも予測する。
- 予測は**最初に解く前に**書いたものだけが意味を持つ。matcha分析のメモに「事前の予測」があれば、それを写す。後から中身を変えない（文言が解決できないときの書き直しだけはよい。その経緯はレポートに書く）。
- 予測の目的は当てることではなく、直観による読みと形式化した構造の食い違いを見つけることである。
- 利用者が書いた行があれば残し、自分の予測は別の名前で加える。
