# matcha-default-extensions

`.matcha` ファイルを受け取り、**決定論的なプログラム**と**AI（あなた）の判断**を分けて、デフォルト論理による論証の検査を行う。

設計原理は「機械的に変換した部分を人が追えること」である。あなたの判断は必ず MEXT の `[ai]` `[extra]` 節に、理由とともに書く。生成部分（`; ===== ここから下は mext.py が自動生成` 以下）は手で直さない。

## 準備

- 道具は Python のパッケージ `mext` にある（依存ライブラリなし）。
  - `python3 -m mext.matcha_check`: 構文チェッカ
  - `python3 -m mext`: デフォルト理論への変換、Extension の計算・検証、Lean 出力
- 最初に `python3 -m mext --help` が動くかを確かめる。動かなければ、次のどちらかをする。
  - `pip install git+https://github.com/JRF-2018/mext` を実行する。
  - このスキルをプラグインとして入れた場合は、プラグインのルート（このスキルのディレクトリの 2 つ上）を `PYTHONPATH` に加える（`export PYTHONPATH=<プラグインのルート>:$PYTHONPATH`）。
- 仕様はこのスキルのディレクトリの `references/` にある。§2 の変換規則は、判断の前に一度読む。
  - `references/matcha_grammar.md`: 文法
  - `references/mext.md`: MEXT の書式、**変換規則**、Extension と preferred の定義
- 引数は次のどれかである。`.matcha` ファイル自体は**書き換えない**。
  - `.matcha` ファイル 1 つ（以下 `X.matcha`）
  - 一つの理論を成す `.matcha` ファイルの組
    - 手順2 で `mext.py init A.matcha B.matcha … -o X.mext` とまとめる。
    - X は最初のファイル名、または利用者が指定した名前にする。
    - 位置は「ファイル名:L12」で表示される。
  - 既存の `X.mext`（`theory:` 行が 1 つ以上あるもの）。手順2 の `init` は省き、そのファイルの `[ai]` `[extra]` `[claimed]` を引き継ぐ。
- 出力はすべて `X.mext` と同じディレクトリに置く: `X.mext`、`X.asis.mext`（必要な場合）、`X.alt-*.mext`（試算した場合）、`X.lean`、`X.sensitivity.md`（感度分析）、`X.report.md`。
- 理論が複数のファイルからなるとき、構文チェックは `python3 -m mext.matcha_check --shared-labels --tree A.matcha B.matcha …` で行う（ファイルをまたぐ `!>` や `:: 優先` のラベルを解決するため）。

## 手順

### 1. 構文チェック（決定論的）

```bash
python3 -m mext.matcha_check --tree X.matcha
```

エラーがあれば、ここで止める。エラーの一覧と直し方の提案だけを含めた `X.report.md` を書いて終える。警告は記録して先へ進む。

### 2. ひな形の作成（決定論的）

```bash
python3 -m mext init X.matcha        # X.mext のひな形（Extension はまだ計算しない）
```

`X.mext` の生成部分（`[atoms]` `[rules]` `[defaults]` `[priority]`）を読み、変換結果を把握する。`init` は、あなたが手順4で独立に予測できるよう、わざと Extension を計算しない。`X.mext` がすでにある場合は、`[ai]` `[extra]` `[claimed]` を引き継いでそのまま手順3へ進む。

### 3. AI の判断を `[ai]` に書く（neuro の部分）

`X.matcha` の原文と `X.mext` の `[atoms]` を見比べて判断する。各行に必ず `; 理由` を付ける。**確信のない同一視はしない**。迷うものは書かずに、レポートの「保留した判断」に挙げる。

文言の指定には、`[atoms]` の `"…"` をそのまま写すほか、別名も使える（ただし `same` / `neg` は原子の文言で書く。別名を書くと警告が出る）。別名とは、ラベル、`#主張名`、要件や結論の素の文言のことである。複数の原子にあたる別名を使うと `mext.py` が候補を示すので、そのときは原子の文言で書き直す。

1. **同一 `same "代表" "別名"`**: 文言は違うが同じ命題を指すもの。
   - **特に**: 別の主張の中で、根拠を書かずに前提として繰り返された要件（「主張A／「要件」」と「主張B／「要件」」）は、ほぼ必ず `same` が必要になる。`[marks]` の「不一致」が手がかりになる。
   - 表記揺れも対象にする。
2. **否定 `neg "A" "B"`**: B が A の否定であるもの。例:「同意している」と「同意していない」、主張と「…は成立しない」という結論。
   - Matcha-D で `>> not` / `>> !` と明示された否定は、すでに `-c` になっているので不要。
3. **結論の型 `failure "文言"` / `effect "文言"`**: `>>` の結論が「成立の効果」か「不成立からの帰結」かについて、既定の読みが誤っている場合だけ書く。既定の読みは、著者の印 `!`、または下位の AND の `!` からの推定である。
   - 著者が `+` を付けながら下位に `!` がある場合（原典の誤記の疑い）は既定が「効果」になるので、必要なら `failure` で正す。
4. **あてはめの審査 `review "対象" ok|doubtful|reject`**: その事実からその評価・要件を導くことに、論理の飛躍がないかを審査する。
   - 対象は二通り:
     - 評価: `[atoms]` の `v` 原子の文言（`"事実@評価"`）
     - 評価のないあてはめ（`「要件」 <= 事実`）: 要件の文言
   - `ok`: 通常の法的評価として成り立つ。
   - `doubtful`: 争いうる。反対の評価もありうる。**誤記が疑われる場合も doubtful にする**。誤記を正した場合の結論は、§6 で試算して示す。
   - `reject`: 明らかな飛躍、または事実と評価がまったく対応しない場合だけに使う。結論が変わりうるので、理由を具体的に書く。
   - `A@占有者` のように人や物を評価して要件上の役割に当てる書き方は、Matcha の通常の書き方である。その場合は、役割の割り当てが事実で支えられているかを審査する。
   - 反対の事情が支持の根拠と同じ AND に並んでいるような構造の問題は、`doubtful` にしたうえで、§6 で構造の問題として述べる。
   - 事実どうしの食い違い（同じファイルの別の行と矛盾する、など）も §6 で指摘する。

5. **争点の共有と独立 `concern 名 "前提" "前提" …` / `distinct "前提" "前提" …`**: 同じ結論を複数の経路が支えるとき（感度分析で「独立した N つの経路」と出たとき）、各経路の要の前提が、内容の上で一つの争点を共有しているか（`concern`）、互いに独立か（`distinct`）を判断して書く。計算の上で経路が複数あることを、そのまま根拠の強さと受け取らないためである。判断できなければ書かない（感度分析が「未判断」と示す）。

6. **結び方 `connective "主張のラベルか要件の文言" 明示|読み`**: 二つ以上を並べた箇所の AND / OR が、原文に明示されているか（「すべて」「いずれか」「以上から」などの手がかりがあるか）、書いた者の読みかを記録する。手がかりがなければ `読み` と書けばよい。根拠を作らない。`mext connectives` が、入れ替えると結論や依存が変わる箇所を示すので、そのうち `読み` と未記録のものを原文で確かめる。
7. **事実の種別 `fact-kind "事実の文言" 記述|仮定|確認済み|著者の主張`**: W に置かれた事実が、原文が事実として述べることか、仮定・思考実験か、原文の外で確かめたことか、著者の評価や仮説が事実の形で書かれたものかを記録する。`仮定` と `著者の主張` は、感度分析で外す候補になる。

8. **補った前提 `supplied "前提の文言" … ; 理由`**: 原文になく、書き起こした者が補った前提を記録する。評価・主張・事実の文言、ラベル、または要件の文言で指す（要件の文言なら、その要件へのあてはめの評価に印が付く）。summary は、結論の決め手が補った前提であれば、そう知らせる。

**背景知識 `[extra]`**: 次の場合には、`rule` / `default` / `fact` を `[extra]` に `; 理由` 付きで書いてよい。

- 足さなければ論証が成り立たない場合。
- 形式的には成り立つが、著者の根拠が結論につながっていない場合。

足した知識はレポートで明示する。新しい事実を例外として扱いたい場合は、`default 名: "前提" : -"原則の結論" / -"原則の結論"` と `priority 名 > 原則のラベル` を組み合わせる。

### 4. Extension の予測を `[claimed]` に書く（やや曖昧な構築）

`solve` を実行する**前に**、原文を読んだ直感で、どのような Extension（可能な判断世界）がありうるかを予測し、主要なリテラルを `[claimed]` に書く。

```
[claimed]
E1*: "主要な結論", -"否定される結論", !"成り立たない主張"   ; 予測の理由
```

- `"X"` は X ∈ E、`-"X"` は ¬X ∈ E、`!"X"` は X ∉ E（立証されていないだけ）を表す。`*` を付けると preferred であることも予測する。
- `solve` の後に、文言が解決できず verify が失敗した場合は書き直してよい。その場合は経緯を §9 に書く。予測の中身（どの結論が成り立つか）は変えない。
- `[claimed]` にすでに行がある場合（利用者が観測などを書いたもの）は消さずに残し、あなたの予測は別の名前で加える。
- `verify` は「いずれかの Extension で成り立つ（信憑的）」を検査する。「すべての Extension で成り立つ（懐疑的）」は `verify --skeptical` で検査する。両方の結果を §9 に書く。

### 5. 求解と検証（決定論的）

```bash
python3 -m mext solve X.mext                 # [ai] を反映した理論
python3 -m mext verify X.mext                # [claimed] の予測は当たったか
python3 -m mext report X.mext                # レポート用の表
python3 -m mext explain X.mext E1 "主要な結論"      # 導出のすべての根拠。含まれない場合は含まれない理由も
python3 -m mext explain X.mext E1 "¬主要な主張"     # 否定は ¬ を前に付ける。たどる深さは --depth N（既定 8）
python3 -m mext lean X.mext                  # X.lean（各 Extension が Γ(E)=E を満たすことの Lean 証明）
```

```bash
python3 -m mext summary X.mext -o X.summary.md           # 一画面の要約と検証の範囲（0.3.1 以降）
python3 -m mext connectives X.mext -o X.connectives.md   # 結び方の感度（0.3.3 以降）
python3 -m mext sensitivity X.mext -o X.sensitivity.md   # 感度分析（0.3.0 以降）: 結論ごとに、どの前提を外すと成り立たなくなるか
```

感度分析は §8（反論の候補）の根拠にする。どの評価を争えば結論が変わるかは、あなたの読みより先に、この出力で確かめる。

- **書かれたとおりの理論**: `[ai]` に `reject` が一つでもあるときは、審査を反映しない版も作って比べる。`reject` がなければ両者は同じになるので、作らずに「同一」と書く。

  ```bash
  cp X.mext X.asis.mext && python3 -m mext solve --no-review X.asis.mext
  python3 -m mext report X.asis.mext
  ```

  `--no-review` を付けて solve すると、ヘッダに `options: no-review` が書かれる。以後は、そのファイルに対するどのコマンドも review を無視する。
- **試算**（§6・§8 のため）: 誤記を正したらどうなるか、抗弁を立証したらどうなるかなどは、`cp X.mext X.alt-名前.mext` で写しを作り、その `[ai]` / `[extra]` を変えて `solve` する。試算はレポートで「試算」と明記する。
- `lean` が使える環境なら `lean X.lean` で確認する（自前の検査器を含むので Mathlib は不要）。使えなければ「未確認」と書く。

### 6. レポート `X.report.md` を書く

日本語で、次の章立てで書く。プログラムの出力（表・導出）と、あなたの判断・解釈を**はっきり区別する**。プログラムの出力は「（mext.py の出力）」と明記して、手を加えずに貼る。

```
# Extension レポート: X.matcha

## 1. 構文チェック          … エラー・警告（matcha_check.py の出力）
## 2. AI の判断（[ai] / [extra]）… same / neg / failure / effect / review と追加知識の一覧表と理由。保留した判断
## 3. デフォルト理論         … mext.py report の「原子命題」「デフォルト」の表
                              （原子が 40 を超えたら要約し、MEXT を参照させる）
## 4. Extension             … 一覧（preferred か否か）と、主要な結論の導出（explain の出力）
## 5. 著者の成否（+ / !）との照合 … 不一致があれば、その原因（原典の誤記か、変換の読みか、AI の判断か）を分析する。
                              印がなければ「印なし」と書き、主要な結論が Extension に含まれるかで代える
## 6. あてはめの実質的妥当性  … review の表。構造の問題・事実の食い違い・誤記の疑い。
                              reject がある場合は書かれたとおりの理論（X.asis.mext）との違い。誤記訂正の試算
## 7. 懐疑的帰結と信憑的帰結
## 8. 反論の候補（立証責任）  … どの評価を争うか、どの例外事実を立証すれば、別の Extension に移るか。
                              sensitivity の表（結論ごとの依存）を貼り、試算があれば示す
## 9. 予測した Extension の検証 … [claimed] と verify の結果。外れた場合はその理由
## 10. 結論                 … summary の「検証の範囲」を添えたうえで、(a) 形式的妥当性（主張された結論が Extension に含まれるか）と
                              (b) 実質的妥当性（評価・背景知識を含めて説得的か）を分けて述べる
```

## 注意

- Extension の数・内容、preferred か否か、著者の印との照合は、**必ず mext.py の出力に従う**。あなたの推論で上書きしない。食い違いに気づいたら、その事実をレポートに書く。
- 原典（`.matcha`）の誤記らしきものを見つけても、ファイルは直さない。レポートで指摘する（訂正の試算は `X.alt-*.mext` で行う）。
- 道具の不具合と思われる挙動に出会ったら、回避策を取ったうえで、レポートの末尾に「道具について」として書く。
