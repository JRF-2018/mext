# mext-analysis（mext分析）

文書を受け取り、三段階で分析する。

1. **matcha分析**: 文書の論証を `X.matcha` に書き起こす（AI の仕事）。
2. **MEXT**: `X.matcha` をデフォルト理論に変換し、Extension を計算・検証する（決定論的）。同一視・否定・あてはめの審査は AI が `[ai]` に理由つきで書く。
3. **レポート**: 文書の論証が、形式的に妥当か、実質的に説得的か、どの前提に依存しているかを述べる（AI の仕事。数字と導出は道具の出力に従う）。

決定論的なのは mext の部分だけで、残りはあなた（AI）の判断である。だからこそ、あなたの判断がどこにあるかを、ファイルの上で人が追えるようにしておく。

## 準備

- 道具は Python のパッケージ `mext` にある。最初に `python3 -m mext --help` が動くかを確かめ、動かなければ `pip install git+https://github.com/JRF-2018/mext` を実行する（プラグインとして入れた場合は、プラグインのルート、つまりこのスキルのディレクトリの 2 つ上を `PYTHONPATH` に加えてもよい）。
- このスキルは、同じプラグインの二つのスキルの手順を使う。先に両方を読む。
  - `../matcha-analysis/SKILL.md`（と、その `references/writing_matcha.md`）: 書き起こしの手順。
  - `../matcha-default-extensions/SKILL.md`（と、その `references/`）: MEXT の手順とレポートの章立て。
- これらのファイルが手元にない場合（ほかの AI や、スキルを入れていない環境から頼まれた場合）は、https://github.com/JRF-2018/mext の `skills/` 以下を読んで、同じ手順に従う。
- 引数: 文書のファイル（以下 `X.md`）、または会話に貼られた文章（`X.source.md` として保存する）。
- 出力は文書と同じディレクトリ（利用者が指定すればそこ）に置く。原文のファイルは書き換えない。

  | ファイル | 内容 |
  |---|---|
  | `X.matcha` | 書き起こし |
  | `X.matcha.md` | 書き起こしのメモ（対応表・補った前提・落としたもの） |
  | `X.mext` | デフォルト理論と Extension（AI の判断は `[ai]`） |
  | `X.asis.mext`、`X.alt-*.mext` | 審査を反映しない版、試算（必要な場合） |
  | `X.v1.matcha`、`X.v1.mext` など | 書き直す前の版（書き直した場合） |
  | `X.summary.md` | 一画面の要約（mext summary の出力） |
  | `X.connectives.md` | 結び方の感度（mext connectives の出力） |
  | `X.sensitivity.md` | 感度分析（mext sensitivity の出力） |
  | `X.lean` | Lean 証明（任意） |
  | `X.mext-analysis.md` | **最終レポート**（これを利用者に返す） |

## 手順

### 1. レポートの長さを決める

文書を読み、レポートがどのくらいの長さになりそうかを見積もる。

- 文書が短く（目安: 5,000 字未満）、主な結論が 3 つ以下なら、聞かずに「標準」にする。
- それより大きい場合は、利用者に聞ける場合は聞く。

  | 選択肢 | 内容 |
  |---|---|
  | 要点 | 本文 2,000 字程度。結論（§0）と、論証の弱点の上位 3 つだけ |
  | 標準 | 本文 6,000 字程度（貼り付けた mext の出力は数えない）。下の章立てをすべて、表は要約して |
  | 詳細 | 長さの制限なし。表と導出を省かずに |

- 聞けない場合（非対話の実行など）は「標準」にし、その旨をレポートの冒頭に書く。
- 書き起こしの範囲（matcha-analysis の手順1）も、ここで一緒に聞いてよい。

### 1.5 すでにある書き起こしの確認

`X.matcha` がすでにある場合（前に matcha分析をした、または人が書いた）は、まず次を確かめる。

```bash
python3 -m mext changed X.check.mext     # 書き起こしの時点から、X.matcha と X.matcha.md が変わったか
```

| `X.matcha` | `X.matcha.md` | 読み取れること | すること |
|---|---|---|---|
| 変わっていない | 変わっていない | 書き起こしのまま | 手順2 を省き、メモを出発点にする（手順3） |
| **変わった** | 変わっていない | 人が書き起こしを直した | 利用者に確かめたうえで、**原文を全部読み直し**、今の `X.matcha` を正として新しいメモを作る（古いメモは `X.matcha.v1.md` などとして残す）。そのうえで `.mext` を新しく作る |
| 変わっていない | **変わった** | 人がメモを直した | メモを `X.matcha` と原文に照らして確かめる。食い違いがあれば、メモの作り直しを利用者に確かめ、提案する |
| **変わった** | **変わった** | 人が両方を直した | 原文を全部読み直し、二つを正として扱う。二つの間や原文との食い違いがあれば、確かめ、提案する |

- 人が直したものは、人の判断である。**上書きしない**。AI が同意できない点は、`X.matcha` を戻さずに、レポートと試算（`X.alt-*.mext`）で示す。
- 利用者に確かめられない場合（非対話の実行など）は、新しいメモを `X.matcha.proposed.md` として別に作り、人の書いたものはそのまま残す。そのことをレポートの冒頭に書く。
- `X.check.mext` がない、または `source:` の記録がない（mext 0.3.3 より前に作られた）場合は、変更を判定できない。メモがあっても、人が直した可能性があるものとして、原文を全部読み直す。
- メモがなく `X.matcha` だけがある場合は、原文を全部読んでメモから作る（原文もなければ、matcha-default-extensions の仕事である）。

### 2. matcha分析

`../matcha-analysis/SKILL.md` の手順1〜7に従い、`X.matcha` と `X.matcha.md` を作る。手順5 の形の点検と磨き上げ（`lint`、`snapshot`、`diff`）は省かない。書き起こしの粗さは、後の段階では取り返せないからである（mext は、一段にまとめられた評価の中身を検査できない）。

### 3. MEXT

`../matcha-default-extensions/SKILL.md` の手順2〜5に従う。

```bash
python3 -m mext init X.matcha                 # X.mext のひな形
# メモの判断を [ai] に移す: 結び方 → connective、事実の種別 → fact-kind（行の注に「書き起こしの判断（X.matcha.md §3）」）
# [ai] に same / neg / failure / effect / review を理由つきで書く
# [claimed] に、メモの「事前の予測」を写す（自分で新しく予測しない。予測は最初に解く前に書いたものだけが意味を持つ）
python3 -m mext solve X.mext
python3 -m mext connectives X.mext -o X.connectives.md   # 結び方の感度: AND / OR を入れ替えると、何が変わるか
python3 -m mext verify X.mext && python3 -m mext verify --skeptical X.mext
python3 -m mext report X.mext
python3 -m mext explain X.mext E1 "主な結論"
python3 -m mext summary X.mext -o X.summary.md           # 一画面の要約: 最終的な結論・対立する命題・決め手・争点・検証の範囲
python3 -m mext sensitivity X.mext -o X.sensitivity.md   # 感度分析: 結論ごとに、何を外すと成り立たなくなるか
python3 -m mext lint X.mext                   # 書き起こしの粗さの最終確認
python3 -m mext lean X.mext                   # 任意。lean があれば lean X.lean で確かめる
```

- **原文に戻るのは、道具が指した箇所である**: 結論を左右する結び方（`connectives` の表）、結論が依存している争点（`summary` の争点）、事実の種別が効いている箇所。そこだけ原文を読み直し、判断が変われば `[ai]` を書き換えて、注を `; 審査で改めた: 理由` にする（メモの判断と違うことが分かるように）。
  - とくに、**結論を左右する結び方で、原文に明示がない（読み）か未記録のもの**は、結論から逆算した結び方でないかを確かめる。確かめた結果は、AND / OR を変えない場合も含めて、レポートの §2 に書く。
- **レポートの §0 は `summary` の出力を土台にして書く**。とくに「検証の範囲」（評価の審査の内訳、対立する命題のない最終的な結論の数）を §0 に必ず書く。対立する命題のない結論は、反対の根拠に勝ったのではなく、反対の根拠が書かれていないだけであることを、言葉を変えずに伝える。
- 感度分析で「独立した N つの経路」が出たら、各経路の要の前提が内容の上で一つの争点を共有しているか（`[ai]` の `concern`）、互いに独立か（`distinct`）を判断して書き、感度分析をやり直す。レポートでは、経路の数を根拠の強さとして書く前に、この判断を示す。
- sensitivity と summary の「複数の経路に共通する判断」に挙がった評価は、あてはめを一か所ずつ外しても結論は残るが、判断ごと採らなければ結論が消えるものである。経路が複数あっても、この判断が一つの弱点になっていることをレポートに書く。
- 「単独で外すと成り立たなくなる」前提と「組の一員」を混同しない。組の一員を、それだけで結論を崩す弱点のように書かない。
- **感度分析がレポートの §0 (c) と §8 の根拠になる**。依存が「—」の結論は、「調べた範囲（表の列）では見つからなかった」と書き、「依存しない」とは書かない。「何に依存しているか」は、あなたの読みではなく `sensitivity` の出力（単独で外すと成り立たなくなる前提、組で外すと成り立たなくなる組、外すと否定が成り立つ前提）から書く。
- **Extension が一つで主な結論が懐疑的帰結に入っても、「論証が正しいと確認された」ことにはならない**。doubtful の評価は推論を止めないし、反対の根拠は書き起こされていなければ理論にない。感度分析で、結論が doubtful の評価や補った前提に依存しているかを必ず確かめ、レポートでそう書く。

- **あてはめの審査（review）は、書き起こした本人として甘くならないように注意する**。書き起こしの段階で `@評価` として表に出した判断こそが、文書の論証の弱点の候補である。
- `X.matcha.md` の「補った前提」は、`[ai]` の審査でも、レポートでも、最も疑うべきものとして扱う。
- 審査や感度分析の途中で書き起こしの誤りや粗さに気づいたら、書き直してよい。その手順:
  1. `python3 -m mext snapshot X.mext` で版を保存する（`X.v1.matcha`、`X.v1.mext`）。
  2. `X.matcha` を直し、`python3 -m mext solve X.mext` で解き直す（`[ai]` と `[claimed]` はそのまま引き継がれる）。
  3. `python3 -m mext diff X.v1.mext X.mext` で、帰結・依存・審査の変化を見る。「効いていない [ai] の判断」が出たら、示された候補の文言に付け替える。
  4. 何を受けて何を直したか、diff で何が変わったかを、`X.matcha.md` の「改訂の記録」に書く。
  - 書き直してよいのは、原文への忠実さと粒度を上げるためだけである。**結論を出すため、または消すために書き直してはならない**。
- `reject` がある場合の `X.asis.mext` と、反論を立証した場合などの試算 `X.alt-*.mext` は、matcha-default-extensions と同じように作る。

### 4. レポート `X.mext-analysis.md` を書く

日本語で、次の章立てで書く。プログラムの出力は「（mext の出力）」と明記して、手を加えずに貼る。あなたの解釈とはっきり区別する。

```
# mext分析: X

（長さ: 要点／標準／詳細。聞けなかった場合はその旨）

## 0. 結論               … 3〜6 行。文書の主な結論は (a) 形式的に導けるか、(b) 実質的に説得的か、
                           (c) 何に依存しているか（決め手になっている評価・補った前提・優先順位）。
                           summary の「検証の範囲」を一行で添える。summary の表を貼ってもよい
## 1. 文書の論証          … 要約と、書き起こした範囲
## 2. 書き起こし（matcha分析）… X.matcha の要所（全文が長ければ抜粋し、ファイルを参照させる）、
                           対応表の要約、補った前提、落としたもの、lint の結果、改訂の記録（diff の要点）、
                           結び方の感度（connectives の表と、明示のない結び方を原文で確かめた結果）、事実の種別。
                           手順1.5 で人の改訂を見つけた場合は、その扱い
## 3. 構文チェック        … （matcha_check の出力）
## 4. AI の判断           … [ai] / [extra] の表と理由。保留した判断
## 5. デフォルト理論と Extension … report の表（原子が 40 を超えたら要約）。Extension の一覧、preferred、
                           主な結論の導出（explain の出力）
## 6. あてはめの実質的妥当性と感度 … review の表。補った前提の審査。sensitivity の表（結論ごとの依存）と、
                           doubtful の評価のうち結論が依存しているもの。asis との違い、試算
## 7. 懐疑的帰結と信憑的帰結
## 8. 反論の候補（立証責任）… どの評価を争えば、どの事実を示せば、結論が変わるか（試算があれば示す）
## 9. 予測した Extension の検証 … [claimed]（メモの事前の予測）と verify の結果。食い違いは発見として、
                           書き起こしの誤り・原文の飛躍・直観の誤りのどれによるかを述べる
## 10. 総評              … 文書の論証の強いところと弱いところ。形式化して初めて見えたこと
## 付録: ファイル一覧
```

「要点」の場合は、§0 と §10 を中心にし、§2〜§9 は弱点の上位 3 つを支える部分だけを残す。

### 5. 返す

レポートの §0 を会話にも書き、ファイルの一覧（パス）を示す。

## 注意

- 会話への返答もファイルも、利用者の言語で書く（指定がなく判断できなければ日本語）。会話への返答は、最初の一文からその言語で書く。

- Extension の数・内容、preferred か否か、懐疑的・信憑的帰結は、**必ず mext の出力に従う**。あなたの推論で上書きしない。
- 書き起こしと審査を同じ AI がすることの限界（自分の書き起こしに甘くなる）を、レポートの §10 で一言述べる。可能なら、利用者に、別の AI か人に `X.matcha` を見てもらうことを勧める。
- 原文にない主張を作らない。原文の論証を強くも弱くもしない。
- 道具の不具合と思われる挙動に出会ったら、回避策を取ったうえで、レポートの末尾に「道具について」として書く。
